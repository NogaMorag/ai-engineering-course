פרק 11: לקוחות עמידים וניידות בין ספקים

כל הקוד שכתבת עד כה הניח שהרשת עובדת, שהשרת עונה, ושאף אחד לא חרג ממכסה. בייצור אף אחת מההנחות האלה לא מחזיקה לאורך זמן. בקשה נכשלת בחמישה־שישה אופנים שונים, וכל אחד דורש תגובה אחרת: יש שגיאות שכדאי לנסות שוב אחריהן, יש כאלה שניסיון חוזר רק יחזור על הטעות, ויש כאלה שעולות כסף גם כשנראה שנכשלו.

הפרק הזה בונה את השכבה שבין היישום לבין ספק המודל: סיווג שגיאות, ניסיונות חוזרים עם המתנה חכמה, זמן קצוב, הזרמה, והתמודדות עם מגבלות קצב. ואז הוא עוטף הכול בממשק אחד, LLMClient, כך ששאר הקורס והפרויקט לא יכירו את Gemini בכלל, ויוכלו לעבור לספק אחר בקובץ אחד. בסופו, נקודת ביקורת 2: כלי שורת פקודה שמסכם כל כתובת, בנוי מכל מה שלמדת בחלק ג.

מה נלמד בפרק

  • מה משתבש בזמן ריצה, ואילו כשלים ראוי לנסות שוב.
  • סיווג שגיאות להיררכיה שלנו, ולמה לא תופסים את השגיאות של הספרייה ישירות.
  • ניסיונות חוזרים: גידול מעריכי, אקראיות, גבול ניסיונות, גבול זמן כולל, ולמה לא פעמיים.
  • זמן קצוב, ומה הוא לא אומר על החיוב.
  • הזרמה: אירועים, זמן לטוקן הראשון מול זמן כולל, ומתי לא להזרים.
  • מגבלות קצב ומקביליות.
  • המתאם (adapter): ממשק אחד, מימוש אמיתי ולקוח מזויף, ומה דולף דרכו.
  • נקודת ביקורת 2: מסכם הכתבות.

ידע מקדים

פרקים 7 עד 10. התרגיל קורא ל־API; החלק האופציונלי דורש ספק שני או Ollama.

11.1 מה משתבש, ומה עושים עם זה

הטבלה הזאת היא לב הפרק. כל השאר הוא מימוש שלה.

מה קרה קוד סיבה טיפוסית לנסות שוב?
בקשה שגויה 400 סכמה לא חוקית, פרמטר לא קיים, הנחיה ריקה לא. אותה בקשה תיכשל שוב
אימות 401, 403 מפתח חסר, שגוי או ללא הרשאה לא. לתקן את הסביבה
לא נמצא 404 שם מודל שגוי לא
חריגה ממכסה 429 יותר מדי בקשות או טוקנים לדקה; מכסה יומית כן, אחרי המתנה. מכסה יומית: לא
שגיאת שרת 500 ואילך תקלה אצל הספק, עומס כן, אחרי המתנה
זמן קצוב, ניתוק אין קוד רשת, שרת איטי, בקשה גדולה כן, אחרי המתנה. אולי כבר חויבת
פלט קטוע סטטוס incomplete max_output_tokens נמוך לא כניסיון חוזר; להגדיל את המגבלה

שני עקרונות יוצאים מהטבלה. הראשון: ניסיון חוזר הוא תרופה לכשל זמני בלבד. 400 ו־401 לא יתוקנו מעצמם; לנסות שוב רק מבזבז זמן ומסתיר את הבאג. השני: כשל לא אומר שלא שילמת. בקשה שקיבלה זמן קצוב אצלך יכולה להסתיים בהצלחה בשרת, והטוקנים שנוצרו מחויבים. ניסיון חוזר הוא בקשה חדשה, עם חיוב חדש.

11.2 סיווג שגיאות להיררכיה שלנו

ספריית ה־SDK זורקת חריגות משלה, אבל במהדורה הנוכחית המחלקות של ממשק ה־Interactions יושבות במודול פרטי, ואי אפשר לייבא אותן בצורה יציבה. גם אם היה אפשר, לא היינו רוצים: אם היישום תופס google.genai.SomethingError, היישום יודע על Gemini, וכשנעבור ספק יישברו עשרים קבצים. הפתרון הוא היררכיה שלנו, והמרה בנקודה אחת:

class LLMError(Exception):
    retryable = False

class LLMRateLimited(LLMError):
    retryable = True

class LLMUnavailable(LLMError):      # 5xx, connection problems, timeouts
    retryable = True

class LLMBadRequest(LLMError):       # 4xx other than 429
    pass

class LLMTruncated(LLMError):        # status == "incomplete"
    pass


def classify(exc: BaseException) -> LLMError:
    status = getattr(exc, "status_code", None)
    if status == 429:
        return LLMRateLimited(str(exc), status_code=status, cause=exc)
    if isinstance(status, int) and status >= 500:
        return LLMUnavailable(str(exc), status_code=status, cause=exc)
    if isinstance(status, int) and 400 <= status < 500:
        return LLMBadRequest(str(exc), status_code=status, cause=exc)
    if isinstance(exc, TimeoutError | ConnectionError) or "Timeout" in type(exc).__name__:
        return LLMUnavailable(str(exc), cause=exc)
    return LLMError(str(exc), cause=exc)

הטריק נקרא טיפוס ברווז (duck typing): במקום לשאול „מאיזו מחלקה אתה”, שואלים „יש לך status_code?”. לחריגות ה־HTTP של כל ספק סביר יש. ההמרה קורית במקום אחד, בתוך GeminiClient, עם except Exception רחב שמיד זורק מחדש כשגיאה שלנו (raise classify(exc) from exc). ה־from שומר את החריגה המקורית בשרשרת, כדי שבעקבות המחסנית (traceback) עדיין יהיה אפשר לראות מה הספרייה אמרה. כל שאר הקוד תופס רק LLMError ובנותיה.

11.3 ניסיונות חוזרים שלא מזיקים

ניסיון חוזר נאיבי, „אם נכשל, נסה שוב מיד”, הוא בעיה: אם הספק עמוס, אלף לקוחות שמנסים שוב באותה שנייה מחמירים את העומס. הדפוס הסטנדרטי הוא גידול מעריכי עם אקראיות (exponential backoff with jitter):

ניסיון תקרת המתנה המתנה בפועל
1 נכשל 1 שנייה אקראי בין 0 ל־1
2 נכשל 2 שניות אקראי בין 0 ל־2
3 נכשל 4 שניות אקראי בין 0 ל־4
4 נכשל 8 שניות, עד תקרה קבועה אקראי בין 0 ל־8

האקראיות („אקראי בין 0 לתקרה”, הצורה שנקראת full jitter) מפזרת את הלקוחות בזמן. התקרה הקבועה (למשל 20 שניות) מונעת המתנות של דקות. ולצידם שני גבולות שחייבים להיות:

  • גבול ניסיונות. ארבעה ניסיונות הם ברירת מחדל סבירה.
  • גבול זמן כולל (deadline). אם ההמתנה הבאה תחרוג מתקציב של, נניח, 90 שניות, מפסיקים. בלי זה, משתמשת מחכה שתי דקות לתשובה שלא תגיע.
def with_retries(operation, policy, *, sleep=time.sleep, clock=time.monotonic, rng=None):
    rng = rng or random.Random()
    started = clock()
    for attempt in range(1, policy.max_attempts + 1):
        try:
            completion = operation()
        except LLMError as err:
            if not err.retryable or attempt == policy.max_attempts:
                raise
            wait = policy.delay(attempt, rng)
            if clock() - started + wait > policy.total_deadline_s:
                raise LLMUnavailable("deadline exhausted") from err
            sleep(wait)
            continue
        completion.attempts = attempt
        return completion

שימי לב ש־sleep, clock ו־rng הם פרמטרים. בבדיקות מזריקים שעון מזויף ושינה שלא ישנה, וכל מדיניות הניסיונות נבדקת באלפית שנייה, בלי רשת ובלי המתנה. זה לא פינוק: קוד ניסיונות חוזרים שלא נבדק הוא בדיוק הקוד שמתגלה כשגוי בשלוש בלילה.

לא פעמיים. ל־SDK יש מנגנון ניסיונות משלו, ובגרסה שהקורס נעול אליה הוא פעיל כברירת מחדל: שלושה ניסיונות (ניסיון אחד ועוד שני ניסיונות חוזרים) על שגיאות שהספרייה מסווגת כזמניות, בעיקר 429 ו־5xx, עם המתנה מעריכית. אם מוסיפים מעליו את with_retries בלי לדעת, מקבלים עד שנים־עשר ניסיונות וזמן המתנה שאי אפשר להסביר. בקורס מכבים את מנגנון הספרייה (attempts=1, שפירושו ניסיון אחד כולל המקורי) ומנהלים את המדיניות במקום אחד, שלנו. הכלל: רכיב אחד הוא הבעלים של הניסיונות החוזרים. אם ספרייה חיצונית עושה את זה טוב, משתמשים בה ולא כותבים מעליה; אם כותבים, מכבים אותה.

אידמפוטנטיות. ניסיון חוזר בטוח רק לפעולות שאפשר לחזור עליהן בלי נזק. קריאה למודל שמייצרת טקסט היא כזאת (למעט העלות). סבב בלולאת כלים שכבר הריץ כלי עם תופעת לוואי, לא. לכן בפרויקט, הניסיונות החוזרים חיים ב־complete, לא סביב לולאת הסוכן.

11.4 זמן קצוב

בלי זמן קצוב (timeout), בקשה שנתקעה תחכה לנצח, והלולאה שמסביבה איתה. הגדרה אחת ברמת הלקוח:

from google.genai import types

http_options = types.HttpOptions(
    timeout=60_000,                                    # milliseconds
    retry_options=types.HttpRetryOptions(attempts=1),  # one attempt: we own the retry policy
)
client = genai.Client(http_options=http_options)

היחידה היא אלפיות שנייה, וזו מלכודת: timeout=60 הוא שישים אלפיות. חישוב שכדאי לעשות פעם אחת ולזכור: בלי גבול זמן כולל, הזמן המרבי לקריאה הוא זמן קצוב כפול מספר ניסיונות, ועוד סכום ההמתנות. עם 60 שניות, ארבעה ניסיונות והמתנות של עד 1, 2 ו־4 שניות, זה עד 247 שניות.

גבול הזמן הכולל מקצר את זה, אבל לא כתקרה קשיחה: הוא נבדק לפני כל המתנה, לא באמצע בקשה. עם גבול של 90 שניות, אחרי שני ניסיונות שנגמרו בזמן קצוב (כ־121 שניות) ההמתנה הבאה כבר חורגת מהתקציב, והלקוח מוותר. אם זה יותר ממה שהמשתמשת תסבול, מקצרים את הזמן הקצוב, את מספר הניסיונות או את גבול הזמן, או מעבירים את העבודה לרקע. בפרויקט, שרץ בלילה בלי משתמשת שמחכה, התקציב נדיב; בכלי שורת הפקודה של נקודת הביקורת, פחות.

ושוב העובדה הלא נעימה: זמן קצוב בצד הלקוח לא מבטל את הבקשה בשרת. אם המודל סיים אחרי 61 שניות, הטוקנים חויבו, והתשובה נזרקה.

11.5 הזרמה

במצב הרגיל, הלקוח מחכה עד שהמודל סיים ומקבל את הכול. ב„הזרמה” (streaming) השרת שולח חלקים (deltas) בזמן שהם נוצרים. למדידה יש שני מספרים שונים:

  • זמן לטוקן הראשון (time to first token, TTFT): כמה מהר המשתמשת רואה שמשהו קורה. בהזרמה הוא לרוב חלק קטן מהזמן הכולל; בהדגמה של התרגיל תמדדי אותו בעצמך.
  • זמן כולל: כמה זמן עד שהתשובה שלמה. הזרמה לא מקצרת אותו; המודל מייצר באותו קצב.
for event in client.interactions.create(model=model, input=prompt, stream=True):
    if event.event_type == "step.delta" and event.delta.type == "text":
        print(event.delta.text, end="", flush=True)
    elif event.event_type == "interaction.completed":
        usage = event.interaction.usage

האירועים שמגיעים, לפי הסדר:

אירוע מה הוא נושא
interaction.created האינטראקציה נפתחה; עדיין אין טקסט
step.start צעד חדש מתחיל
step.delta חלק מהתוכן; לטקסט, delta.type הוא text והטקסט ב־delta.text
step.stop הצעד הסתיים
interaction.completed האינטראקציה המלאה, ובה הסטטוס והשימוש
error תקלה באמצע הזרם

את השימוש בטוקנים מקבלים רק בסוף, באירוע האחרון.

מתי להזרים? כשיש אדם שמחכה: צ׳אט, עוזר בעורך, כלי אינטראקטיבי. מתי לא? כשהקוד הוא שממשיך: צינור לילי, פלט מובנה (JSON חלקי לא שווה כלום עד שהוא שלם), או קריאות שהתוצאה שלהן נשמרת ולא מוצגת.

בפרויקט אין משתמשת שמחכה, ולכן אין הזרמה; בלקוח היא קיימת כדי שתכירי אותה, וההדגמה של התרגיל מריצה אותה פעם אחת ומודדת זמן לטוקן ראשון. בכלי summarize_url אין הזרמה, כי הפלט שלו מובנה. עוד כלל: הזרמה לא מנוסה שוב באמצע. אם הזרם נשבר אחרי מחצית התשובה, אי אפשר „להמשיך מאותו מקום”; מתחילים מחדש, ומה שכבר הודפס צריך להימחק או להתווסף אליו הסבר.

11.6 מגבלות קצב ומקביליות

השכבה החינמית מגבילה בקשות לדקה, טוקנים לדקה, ובקשות ליום, והמספרים המדויקים מופיעים רק ב־AI Studio ומשתנים. כמה כללים שעובדים בכל מדרגה:

  • 429 הוא מידע, לא כישלון. ההמתנה המעריכית מטפלת בו; אם מגיעה כותרת Retry-After מכבדים אותה (בלקוח של התרגיל זה לא ממומש, וזו הרחבה טובה). מכסה יומית שנגמרה היא עניין אחר: לא מנסים שוב, מדווחים ומסיימים.
  • מקביליות מבוקרת. עשרים כתבות במקביל הן עשרים בקשות באותה שנייה. סמפור של שתיים או שלוש בקשות בו־זמנית, או פשוט לולאה סדרתית עם המתנה קצרה, מספיקים לפרויקט. בחלק ח נדבר על תור.
  • פחות בקשות. דה־דופליקציה לפני סיכום (חלק ד) ושמירה במטמון של תשובות זהות (חלק ח) חוסכות יותר מכל כוונון של ניסיונות חוזרים.
  • לרשום שימוש. כל קריאה רושמת טוקנים ומספר ניסיונות. בלי זה, „למה קיבלנו 429” היא שאלה בלי תשובה.

11.7 המתאם: ממשק אחד, ספק אחד בקובץ אחד

כל מה שלמעלה מתכנס לקובץ אחד, llm_client.py, ולשלוש מחלקות:

class LLMClient(Protocol):
    def complete(self, prompt, *, system=None, max_output_tokens=1024, temperature=0.2, response_format=None) -> Completion: ...
    def stream(self, prompt, *, system=None, max_output_tokens=1024) -> Iterator[str]: ...


class GeminiClient:      # the real one: timeouts, classify, with_retries, streaming
    ...


@dataclass
class FakeClient:        # scripted answers (or exceptions) for tests; never touches the network
    script: list[str | Exception]

Protocol (הכרת אותו בקוד של תרגיל פרק 7) מגדיר את החוזה בלי ירושה: כל מחלקה עם אותן מתודות מקיימת אותו. GeminiClient מממש אותו מול Gemini. FakeClient מממש אותו מתוך תסריט: רשימה של תשובות או חריגות, כדי שבדיקה תוכל לומר „הקריאה הראשונה מחזירה 429, השנייה JSON תקין”. כל שאר הקורס מקבל LLMClient כפרמטר ולא מייבא google.genai לעולם.

מה המתאם מסתיר היטב: אימות, ניסיונות חוזרים, זמן קצוב, הזרמה, שגיאות. מה דולף דרכו, וכדאי לדעת מראש:

דולף למה מה עושים
שמות מודלים לכל ספק שמות משלו משתני סביבה, לא מחרוזות בקוד
ניב הסכמות ספקים תומכים בתת־קבוצות שונות של JSON Schema סכמות שטוחות, בלי הפניות
ספירת טוקנים טוקנייזרים שונים, מחירים שונים למדוד אצל כל ספק מחדש
פורמט הכלים שמות שדות שונים לקריאה ולתוצאה מתאם נפרד ללולאת הכלים, אם צריך
איכות אותה הנחיה, תוצאות שונות ההערכות של חלק ה רצות מחדש אחרי החלפת ספק

ניידות היא לא „החלפה בלי מחשבה”; היא „החלפה בקובץ אחד, ואז הרצת ההערכות”.

ספק שני, אופציונלי. ל־Gemini יש נקודת קצה תואמת OpenAI, שעובדת עם אותו מפתח. עם חבילת openai אפשר לכתוב מימוש שני של LLMClient בעשרים שורות, או להצביע על Ollama מקומי בשינוי כתובת:

from openai import OpenAI

client = OpenAI(
    api_key=os.environ["GEMINI_API_KEY"],
    base_url="https://generativelanguage.googleapis.com/v1beta/openai/",
)
response = client.chat.completions.create(
    model="gemini-3.5-flash-lite",
    messages=[{"role": "user", "content": prompt}],
    max_tokens=300,
)
text = response.choices[0].message.content

מול Ollama מקומי משנים שלושה דברים: הכתובת, המפתח (כל מחרוזת מתקבלת) ושם המודל:

client = OpenAI(api_key="ollama", base_url="http://localhost:11434/v1")
model = "<local-model>"  # pick a name from: ollama list

העניין בתרגיל האופציונלי הוא לא הקוד אלא ההשוואה: אותה הנחיה, אותה סכמה, ולראות מה השתנה.

11.8 המינימום של תצפיתיות

חלק ח יעסוק במעקב (tracing) ברצינות. כבר עכשיו, שלושה דברים נרשמים בכל קריאה, כי בלעדיהם אי אפשר לדבג כלום:

  • מספר הניסיונות ואילו שגיאות היו בדרך (on_retry בלקוח מדפיס שורה).
  • זמן התגובה.
  • טוקנים בכניסה וביציאה.

Completion נושא את כולם. בפרויקט הם ייכתבו לטבלה; בכלי שורת הפקודה הם מודפסים לשגיאה הסטנדרטית (stderr), כדי לא לערבב אותם בפלט.

11.9 נקודת ביקורת 2: מסכם הכתבות

כל חלק ג נפגש בכלי אחד: summarize_url.py. נותנים לו כתובת, מקבלים פריט עיתון.

שלב מאיפה מה
הורדה וחילוץ פרק 10, fetch_url אימות הכתובת, הורדה עם זמן קצוב, חילוץ הטקסט המרכזי

הכלי מחזיר קודי יציאה שונים: 0 להצלחה, 2 כשהדף אינו כתבה, 3 כשהמודל נכשל, 4 כשההורדה נכשלה. קוד שקורא לכלי (וב־GitHub Actions, בחלק ז, זה יקרה) יודע מה קרה בלי לפרסר הודעות. הבדיקות רצות בלי רשת: FakeClient מספק את התשובות, קובץ מקומי מחליף את ההורדה. ההרצה החיה על שלוש כתובות היא הדבר היחיד שדורש מפתח.

סיכום

  • כשל הוא קטגוריה, לא אירוע: 4xx לא מנסים שוב, 429 ו־5xx וזמן קצוב מנסים, קטוע מגדילים.
  • ממירים שגיאות ספק להיררכיה שלנו בנקודה אחת, לפי status_code.
  • ניסיונות חוזרים: גידול מעריכי עם אקראיות, גבול ניסיונות, גבול זמן כולל, רק לכשלים זמניים, ורק רכיב אחד הוא הבעלים. מנגנון הספרייה כבוי.
  • זמן קצוב באלפיות שנייה; הזמן המרבי הוא זמן קצוב כפול ניסיונות ועוד המתנות; כשל לא אומר שלא חויבת.
  • הזרמה משפרת זמן לטוקן ראשון, לא זמן כולל; לא לפלט מובנה ולא לצינורות; לא מנוסה שוב באמצע.
  • LLMClient הוא הגבול: GeminiClient מולו, FakeClient לבדיקות, ושאר הקוד לא מכיר ספק.

מונחים לזכור

טעויות נפוצות

  • לנסות שוב על 400. הבקשה שגויה; הניסיון החוזר מסתיר את הבאג ומבזבז זמן.
  • ניסיונות חוזרים בשתי שכבות. הספרייה כבר מנסה שלוש פעמים כברירת מחדל. בעלים אחד, לא שניים.
  • timeout=60 וחשיבה בשניות. היחידה היא אלפיות שנייה.
  • להניח שזמן קצוב מבטל חיוב. השרת ממשיך; הטוקנים נספרים.
  • לתפוס Exception בכל מקום. רק בגבול ההמרה, וממנו החוצה רק LLMError.
  • להזרים פלט מובנה. JSON חלקי לא שימושי; מחכים לסוף.
  • ליבא את ספריית הספק מחוץ ללקוח. זה מה שהופך „להחליף ספק” לפרויקט של שבוע.

שאלות ראיון

  1. אילו שגיאות תנסי שוב, ואיך? רק כשלים זמניים: 429, 5xx, זמן קצוב וניתוק. עם המתנה מעריכית ואקראיות, גבול ניסיונות, וגבול זמן כולל. 4xx אחרים לא; פלט קטוע מקבל מגבלה גדולה יותר. ורק רכיב אחד הוא הבעלים של המדיניות, כדי לא לנסות פעמיים בשתי שכבות.

המשך: ו־429 שנובע ממכסה יומית? זה לא כשל זמני בסקאלה של שניות, וניסיון חוזר רק שורף זמן; מזהים אותו לפי הודעת השגיאה או לפי המתנה ארוכה שהספק מבקש, מדווחים ומסיימים את הריצה.

  1. מה ההבדל בין זמן לטוקן ראשון לזמן כולל, ומתי הזרמה עוזרת? זמן לטוקן ראשון הוא מתי המשתמשת רואה משהו; זמן כולל הוא מתי התשובה שלמה. הזרמה מקצרת את הראשון בלבד. היא עוזרת כשאדם מחכה, ולא בצינורות, בפלט מובנה או בקריאות שתוצאתן נשמרת.
  2. איך בונים לקוח שאפשר להחליף בו ספק? ממשק שלנו (Protocol) עם complete ו־stream; מימוש לכל ספק שממיר שגיאות להיררכיה שלנו בנקודה אחת; לקוח מזויף לבדיקות; שאר הקוד לא מייבא ספרייה של ספק. ומודעות למה שדולף: שמות מודלים, ניב סכמות, ספירת טוקנים, ואיכות, שדורשת הרצת הערכות מחדש.
  3. למה זמן קצוב לא מבטיח שלא שילמת? כי הוא מתרחש אצלי. השרת ממשיך לייצר, מסיים, ומחייב. ניסיון חוזר הוא בקשה שנייה, בתשלום שני. לכן מתכננים את התקציב מראש: זמן קצוב כפול ניסיונות ועוד המתנות.

המשך: אז איך בכל זאת מגבילים את העלות? לפני הקריאה: גבול פלט וקיצוץ קלט. אחריה: רישום שימוש בכל קריאה, ושומר תקציב שעוצר את הריצה כשהסכום עובר סף (פרק 23).

פתק Obsidian

הפתק המוכן נמצא גם כקובץ: obsidian/11-robust-clients.md. זה תוכנו:

  • טבלת הכשלים: 400/401/404 לא מנסים; 429 ו־5xx וזמן קצוב מנסים אחרי המתנה; incomplete מגדילים מגבלה.
  • היררכיה שלנו: LLMError ובנותיה, המרה ב־classify לפי status_code, בנקודה אחת.
  • ניסיונות: מעריכי עם אקראיות, 4 ניסיונות, תקרה 20 שניות, גבול כולל 90. רכיב אחד הבעלים; הספרייה כבויה (attempts=1).
  • זמן קצוב באלפיות שנייה. המקסימום הוא זמן קצוב כפול ניסיונות ועוד המתנות; גבול הזמן הכולל קוצר אותו. כשל לא מבטל חיוב.

תרגיל

מטרה: לבנות את llm_client.py עם היררכיית שגיאות, ניסיונות חוזרים נבדקים, זמן קצוב והזרמה; לעטוף אותו ב־LLMClient עם לקוח מזויף; ואז לסגור את חלק ג עם summarize_url.py. זמן: שלושה ימי לימוד (ימים 17 עד 19), כ־60 דקות בנייה בשני הראשונים ו־120 דקות בנקודת הביקורת. ידע מקדים: הפרק, מפתח API, וחיבור לרשת.

הצעדים, קוד ההתחלה, הרמזים והפתרון נמצאים ב־ exercises/ch11-production-client/README.md.

קריטריון סיום:

  • ההדגמה מראה: קריאה רגילה עם מספר ניסיונות וזמן; הזרמה עם זמן לטוקן ראשון; שגיאת 404 שלא מנוסה שוב; וקיטוע שמדווח.
  • תשע הבדיקות עוברות בלי רשת: סיווג, המתנה, ניסיונות רק לכשלים זמניים, גבול ניסיונות וגבול זמן, הלקוח המזויף, וקודי היציאה של הכלי.
  • summarize_url.py רץ על שלוש כתובות חיות; הפלט נשמר בפתק עם הטוקנים והניסיונות של כל אחת.
  • בפתק: החישוב של הזמן המרבי לקריאה עם ההגדרות שלך.
