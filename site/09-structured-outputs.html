פרק 9: פלט מובנה

עד עכשיו המודל החזיר טקסט, ואנחנו קראנו אותו בעיניים. תוכנה לא קוראת בעיניים. ברגע שקוד צריך להמשיך לעבוד עם התשובה, לשמור אותה, לדרג אותה, לשלוח אותה במייל, צריך צורה מוסכמת מראש.

„פלט מובנה” (structured output) הוא המנגנון שבו המודל מתחייב לצורה: סכמת JSON שמוגדרת בקוד, שהשרת אוכף בזמן היצירה, ושאנחנו מאמתים שוב בצד שלנו. הפרק מלמד להגדיר את הצורה פעם אחת, לקבל אותה בחזרה, לדעת בדיוק מה מובטח ומה לא, ולתקן בצורה מסודרת כשמשהו לא עומד בכללים. בסופו תבני את ArticleSummary, הצורה של פריט אחד בעיתון הבוקר.

מה נלמד בפרק

  • ארבע המשמעויות של „פלט תקין”, ומי אוכף כל אחת.
  • JSON Schema בעשר דקות, ומה המודל רואה ממנו.
  • Pydantic כמקור אמת יחיד: מודל אחד משרת גם את הבקשה וגם את האימות.
  • מה דקידוד מוגבל (constrained decoding) מבטיח, ומה הוא לא יכול להבטיח.
  • אימות, ניסיון תיקון אחד, וויתור מסודר.
  • עיצוב סכמות שמודלים ממלאים טוב.
  • פלט מובנה מול קריאה לכלים: אותו מנגנון, שתי מטרות.

ידע מקדים

פרק 8. היכרות עם Pydantic עוזרת אבל לא נדרשת; מה שצריך מוסבר כאן. התרגיל קורא ל־API.

9.1 ארבע משמעויות של „פלט תקין”

בפרק 8 ביקשנו סיכום בפורמט קבוע: כותרת, שלוש נקודות, משפט „למה זה חשוב”. הבקשה הייתה בטקסט, והתשובה הייתה בטקסט. כדי להמשיך משם בקוד היינו צריכים לפרסר (parse) את הטקסט: למצוא את הכותרת, לספור נקודות, לקוות שאין שורה מיותרת. זה נשבר מהר. אפשר לבקש JSON בהנחיה, וזה עובד לעיתים קרובות, אבל „לעיתים קרובות” הוא בדיוק מה שלא רוצים בקוד. דוגמאות למה שקורה כשמבקשים JSON בטקסט חופשי:

  • המודל עוטף את ה־JSON בגדר של Markdown, ו־json.loads נכשל.
  • המודל מוסיף משפט פתיחה: „הנה ה־JSON שביקשת:”.
  • השדה נקרא title במקום headline, או שהוא מחרוזת במקום רשימה.
  • יש שתי נקודות במקום שלוש.
  • הכול תקין מבחינה טכנית, ואחת העובדות לא מופיעה בכתבה.

הרשימה הזאת מסתירה ארבע רמות שונות של „תקין”, וחשוב להפריד ביניהן כי כל אחת נאכפת במקום אחר:

רמה השאלה מי אוכף
1. נפרס (parses) האם זה JSON חוקי? סכמה בבקשה; ו־json.loads אצלנו
2. תואם סכמה (schema-valid) שמות שדות, טיפוסים, שדות חובה, ערכים מתוך רשימה סגורה סכמה בבקשה; ו־Pydantic אצלנו
3. מקיים כללים (business rules) „בדיוק שלוש נקודות”, „כותרת עד 12 מילים”, „מתחיל ב־Why it matters” הקוד שלנו
4. נאמן למקור (faithful) האם העובדות באמת מופיעות בכתבה? הערכה (חלק ה). שום סכמה לא בודקת אמת

הפרק הזה סוגר את רמות 1 עד 3. רמה 4 היא נושא של חלק ה, וחשוב לזכור את זה: פלט שעבר את כל האימותים עדיין יכול להיות שקר מנוסח יפה.

9.2 JSON Schema בעשר דקות

JSON Schema הוא תקן לתיאור צורה של JSON. לא צריך את כולו; לצורך עבודה עם מודלים מספיק תת־קבוצה קטנה. כך נראית סכמה של אובייקט עם שלושה שדות:

{
  "type": "object",
  "properties": {
    "is_article": {"type": "boolean", "description": "False for ads, error pages, empty pages."},
    "headline": {"type": "string", "description": "At most 12 words, in your own words."},
    "confidence": {"type": "string", "enum": ["high", "medium", "low"]}
  },
  "required": ["is_article", "headline", "confidence"]
}

המילים שחשוב להכיר:

מילת מפתח משמעות
type אחד מתוך object, array, string, number, integer, boolean
properties השדות של אובייקט, כל אחד עם סכמה משלו
required אילו שדות חייבים להופיע
items הסכמה של כל איבר במערך
enum רשימה סגורה של ערכים מותרים
description טקסט חופשי. המודל קורא אותו; זו התיעוד של השדה

שתי עובדות על איך המודל משתמש בסכמה. ראשית, השרת משתמש בה כדי להגביל את היצירה לצורה שהסכמה מתירה (דקידוד מוגבל, constrained decoding); התיאור המקובל הוא שבכל צעד נבחרים רק טוקנים שעדיין יכולים להוביל ל־JSON תקין, אבל המימוש המדויק הוא של הספק, ומה שמובטח לך הוא התוצאה: JSON תואם. שנית, המודל קורא את הסכמה כטקסט, כולל התיאורים, ולכן description טוב משפר את התוכן, לא רק את הצורה. סכמה בלי תיאורים היא כמו פונקציה בלי שמות פרמטרים.

מה כדאי להימנע ממנו:

  • הפניות בין חלקי הסכמה ($ref ו־$defs).
  • קינון עמוק.
  • ביטויים רגולריים (pattern).
  • פורמטים של מחרוזת כמו date-time.

חלקם לא נתמכים בכל ספק, וחלקם נתמכים אבל פוגעים באיכות המילוי. כל כלל כזה עובר לרמה 3, לקוד שלנו.

9.3 Pydantic כמקור אמת יחיד

לכתוב סכמת JSON ביד ואז לכתוב מחלקה שמייצגת אותה בפייתון זה כפל, ובכפל יש סחף. Pydantic פותר את זה: כותבים מחלקה אחת, מפיקים ממנה את הסכמה לבקשה, ומאמתים איתה את התשובה.

from typing import Literal

from pydantic import BaseModel, Field

Confidence = Literal["high", "medium", "low"]


class ArticleSummary(BaseModel):
    is_article: bool = Field(description="False for ads, error pages, empty or broken pages.")
    headline: str = Field(description="At most 12 words, in your own words. Empty string if not an article.")
    bullets: list[str] = Field(description="Exactly three one-sentence facts taken from the article.")
    why_it_matters: str = Field(description="One sentence that starts with 'Why it matters:'.")
    tags: list[str] = Field(description="One to four short lowercase topic tags.")
    confidence: Confidence = Field(description="How well the article text supports the summary.")

מה כל חלק עושה:

  • Literal["high", "medium", "low"] הופך ל־enum בסכמה. רשימה סגורה בקוד היא רשימה סגורה למודל.
  • Field(description=...) הופך ל־description. זו ההנחיה של השדה; כותבים אותה כמו כלל, לא כמו שם.
  • list[str] הופך ל־array עם items מסוג מחרוזת.

הסכמה מופקת בשורה אחת, ואז עוברת ניקוי קטן: Pydantic מוסיף לכל שדה מפתח title עם שם השדה כשם תצוגה (למשל Is Article). זה רעש שעולה טוקנים ולא מוסיף כלום, אז מסירים אותו (הפונקציה clean_schema בתרגיל עושה את זה רקורסיבית). התיאורים נשארים.

RESPONSE_FORMAT = {
    "type": "text",
    "mime_type": "application/json",
    "schema": clean_schema(ArticleSummary.model_json_schema()),
}

interaction = client.interactions.create(
    model=model,
    input=prompt,
    system_instruction=SYSTEM,
    response_format=RESPONSE_FORMAT,
    generation_config={"temperature": 0.1, "max_output_tokens": 600},
)
summary = ArticleSummary.model_validate_json(interaction.output_text)

הפרמטר response_format אומר לשרת: הפלט הוא טקסט מסוג JSON, והוא חייב להתאים לסכמה הזאת. בצד השני, model_validate_json עושה את שלוש העבודות בבת אחת: פרסור, בדיקת סכמה, והרצת כללי האימות שנכתוב בסעיף הבא. אם משהו נכשל נזרקת ValidationError עם הודעה מדויקת: איזה שדה, מה היה, מה ציפו.

9.4 מה המודל מבטיח, ומה לא

כשהבקשה כוללת סכמה והסטטוס שחוזר הוא completed, הפלט נפרס ותואם את הסכמה. זו הבטחה של המנגנון, לא של המזל: רמות 1 ו־2 סגורות. ובכל זאת מאמתים גם אצלנו: האימות זול, והוא תופס גם את מה שהסכמה לא מבטאת. מכאן מתחילות ההסתייגויות, וכדאי לדעת אותן בעל פה.

הסכמה לא אוכפת מה שהיא לא מבטאת. „בדיוק שלוש נקודות” אפשר לבטא בסכמה (המילים minItems ו־maxItems), אבל לא כל ספק מכבד את זה בדקידוד. „כותרת עד 12 מילים” או „מתחיל במילים Why it matters” אי אפשר לבטא כלל. את הכללים האלה הקוד שלנו בודק.

הסכמה לא אוכפת אמת. confidence: "high" הוא שיפוט של המודל, לא מדידה. עובדה בנקודה שלישית יכולה להיות מומצאת ולעבור כל אימות.

פלט קטוע הוא לא פלט. אם max_output_tokens נמוך מדי, היצירה נעצרת באמצע והסטטוס הוא incomplete. ה־JSON חתוך, ושום ניסיון תיקון לא יעזור; הפתרון הוא להגדיל את המגבלה. לכן בודקים את הסטטוס לפני שמנסים לפרסר.

סכמה גורמת למודל למלא טופס גם כשאין מה למלא. אם הקלט הוא דף שגיאה, מודל שחייב להחזיר כותרת ושלוש נקודות ימציא אותן. לכן יש בסכמה שדה is_article: דרך חוקית להגיד „לא”. כלל אצבע: לכל סכמה צריך להיות מוצא מכובד למקרה שהמשימה לא ישימה; אחרת המודל ימציא את התשובה.

9.5 אימות, ניסיון תיקון אחד, וויתור

הכללים שהסכמה לא מבטאת נכתבים כמאמת (validator) על המודל של Pydantic, ורצים אוטומטית בתוך model_validate_json:

from pydantic import model_validator


class ArticleSummary(BaseModel):
    ...

    @model_validator(mode="after")
    def check_rules_the_schema_cannot_express(self) -> "ArticleSummary":
        if self.is_article:
            if len(self.bullets) != 3:
                raise ValueError("an article needs exactly three bullets")
            if len(self.headline.split()) > 12:
                raise ValueError("the headline must be at most 12 words")
            if not self.why_it_matters.startswith("Why it matters:"):
                raise ValueError("why_it_matters must start with 'Why it matters:'")
        elif self.headline.strip() or self.bullets or self.why_it_matters.strip():
            raise ValueError("a non-article must have an empty headline, bullets and why_it_matters")
        return self

ומה עושים כשהאימות נכשל? המדיניות בקורס ובפרויקט היא „ניסיון תיקון אחד, ואז ויתור בקול”:

צעד מה קורה
1 קוראים למודל עם ההנחיה והסכמה
2 אם הסטטוס incomplete: זורקים שגיאת קיטוע. לא מנסים שוב
3 מריצים model_validate_json. הצליח: מחזירים את האובייקט
4 נכשל: בונים הנחיית תיקון: ההנחיה המקורית, הפלט הפסול, והודעת המאמת כלשונה
5 קוראים שוב. הצליח: מחזירים. נכשל: זורקים שגיאה עם ההודעה האחרונה

למה בדיוק ניסיון אחד? כי כישלון שני כמעט תמיד אומר שהסכמה או ההנחיה לא ברורות, לא שהיה חוסר מזל, ולולאה לא תפתור בעיית הגדרה. כי כל ניסיון עולה טוקנים וזמן. וכי לולאה בלי גבול היא באג שמחכה לחשבון. למה לצרף את הודעת המאמת? כי היא מדויקת („an article needs exactly three bullets”) ומודלים מתקנים לפי הודעה כזאת היטב. למה לזרוק ולא להחזיר אובייקט חלקי? כי הקוד שממשיך אחרינו חייב לדעת שמה שהוא מקבל תקין. בעיתון הבוקר עדיף לדלג על פריט מאשר להדפיס פריט שבור.

9.6 עיצוב סכמה שמודלים ממלאים טוב

  • שטוחה. אובייקט אחד עם שדות פשוטים. קינון של שתי רמות הוא המקסימום הנוח.
  • תיאור שהוא כלל. „Exactly three one-sentence facts taken from the article” עדיף על „the bullets”.
  • רשימות סגורות ל־enum. כל ערך שאפשר למנות מראש, מונים. זה מונע וריאציות כמו High ו־high.
  • סדר השדות הוא סדר החשיבה. is_article ראשון: המודל מחליט אם זו כתבה לפני שהוא ממלא כותרת. הסדר בסכמה הוא בדרך כלל הסדר שבו המודל כותב.
  • מוצא מכובד. שדה שמאפשר למודל לומר „לא ישים” במקום להמציא.
  • להפריד ידיעה משיפוט. עובדות בשדה אחד, confidence בשדה אחר. כך אפשר להשתמש בשיפוט בלי לערבב אותו בתוכן.
  • רשימות עם גבול. „one to four tags”, לא „tags”. בלי גבול מודלים נוטים להאריך.
  • לא לבקש עולם בקריאה אחת. אובייקט של ארבעים שדות הוא סימן לפרק משימה, לפי פרק 8.

9.7 פלט מובנה מול קריאה לכלים

בפרק הבא המודל יבקש להפעיל פונקציות. גם זה, מתחת למכסה, פלט מובנה: המודל מייצר JSON שתואם לסכמת הפרמטרים של הפונקציה. ההבדל הוא במטרה ובזרימה:

פלט מובנה קריאה לכלים
מה המודל מייצר את התשובה עצמה, בצורה ידועה בקשה לפעולה, עם ארגומנטים
מי ממשיך הקוד שלנו, עם האובייקט הקוד שלנו מריץ, ומחזיר תוצאה למודל להמשך
כמה סבבים אחד כמה שצריך, עם גבול
דוגמה סיכום כתבה „הורד את הדף הזה ואז סכם אותו”

כלל אצבע: אם את יודעת מראש איזו צורה את צריכה ואין פעולות באמצע, פלט מובנה. אם המודל צריך לבחור מה לעשות או לקבל מידע נוסף תוך כדי, כלים.

9.8 בפרויקט

ArticleSummary היא הצורה של פריט אחד בעיתון הבוקר, והיא תלווה אותנו עד הסוף:

  • בחלק ד, הטקסט של headline ו־bullets יהפוך ל־embedding לזיהוי כפילויות.
  • בחלק ה, confidence וזוג העובדות ישמשו להערכות: האם העובדות באמת בכתבה.
  • בחלק ו, הסוכן יחליט לפי tags ו־confidence אילו פריטים ראויים למחקר נוסף.
  • האחסון יהיה שורות JSON ב־SQLite: model_dump_json בכניסה, model_validate_json ביציאה.

החלטה אחת שכבר נלקחה כאן ותתברר כחשובה: שדה is_article. בלעדיו, כל דף שגיאה ברשימת הקריאה היה הופך לפריט בעיתון.

סיכום

  • „תקין” הוא ארבע רמות: נפרס, תואם סכמה, מקיים כללים, נאמן למקור. הסכמה סוגרת שתיים; הקוד שלנו את השלישית; ההערכה את הרביעית.
  • מודל Pydantic אחד הוא מקור האמת: ממנו הסכמה לבקשה, ואיתו האימות של התשובה.
  • דקידוד מוגבל מבטיח צורה כשהסטטוס completed. פלט incomplete הוא קטוע ולא מתקנים אותו.
  • כללים שהסכמה לא מבטאת נכתבים כמאמת; כשהוא נכשל, ניסיון תיקון אחד עם הודעת השגיאה, ואז ויתור בקול.
  • סכמה טובה: שטוחה, עם תיאורים שהם כללים, רשימות סגורות, סדר שדות הגיוני, ומוצא מכובד.

טעויות נפוצות

  • לבקש JSON בהנחיה ולפרסר בתקווה. בלי סכמה בבקשה אין הבטחה; עם סכמה יש.
  • לחשוב שסכמה מבטיחה נכונות. היא מבטיחה צורה. העובדות הן עניין להערכה.
  • לנסות לתקן פלט קטוע. סטטוס incomplete דורש מגבלה גדולה יותר, לא קריאה חוזרת.
  • לולאת תיקון בלי גבול. ניסיון אחד. כישלון שני הוא בעיית הגדרה.
  • סכמה בלי דרך להגיד „לא”. המודל ימלא את הטופס גם על דף שגיאה.
  • לכתוב סכמה ביד ליד המחלקה. שני מקורות אמת נסחפים זה מזה. מודל אחד, סכמה מופקת.

שאלות ראיון

  1. מה ההבדל בין פלט שתואם סכמה לפלט נכון? תואם סכמה: נפרס, שמות וטיפוסים נכונים, ערכים מתוך הרשימות המותרות. נכון: גם מקיים כללי עסק שהסכמה לא מבטאת, וגם נאמן למקור. את השתיים הראשונות השרת מבטיח; את השלישית הקוד שלי בודק; הרביעית נמדדת בהערכות.

המשך: ואיך בודקים את הרמה הרביעית בפועל? משווים כל עובדה בפלט למקור: בעין על מדגם, או עם מודל שופט על כל הפלטים, ומודדים אחוז. זה חלק ה; שום בדיקה בזמן ריצה לא מחליפה את זה.

  1. איך את מטפלת בפלט שנכשל באימות? בודקת קודם שהוא לא קטוע; אם כן, מגדילה את מגבלת הטוקנים. אחרת ניסיון תיקון אחד עם ההנחיה המקורית, הפלט הפסול והודעת המאמת כלשונה. אם גם הוא נכשל, זורקת שגיאה ולא מחזירה אובייקט חלקי.

המשך: למה לא שלושה ניסיונות? כי כישלון שני כמעט תמיד מצביע על הגדרה לא ברורה בסכמה או בהנחיה, ולולאה רק מסתירה את זה ועולה טוקנים. מתקנים את ההגדרה, לא את מספר הניסיונות.

  1. למה Pydantic ולא סכמת JSON ידנית? מקור אמת אחד: אותה מחלקה מפיקה את הסכמה לבקשה ומאמתת את התשובה, כולל כללים שסכמה לא מבטאת. בלי זה שני ייצוגים נסחפים זה מזה.
  2. מתי תעדיפי פלט מובנה ומתי קריאה לכלים? כשאני יודעת מראש איזו צורה אני צריכה ואין פעולות באמצע: פלט מובנה. כשהמודל צריך לבחור פעולה או לקבל מידע תוך כדי: כלים. מתחת למכסה שניהם JSON לפי סכמה; ההבדל הוא הלולאה.
