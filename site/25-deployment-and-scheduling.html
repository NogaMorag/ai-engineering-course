פרק 25: פריסה ותזמון

עיתון בוקר שצריך להריץ ביד הוא לא עיתון בוקר. הפרק הופך את הקוד למשימה שרצה בלי אדם: קונפיגורציה לפי סביבה, GitHub Actions עם תזמון (ועם המלכודת של שעון קיץ), סודות, תוצרים (artifacts) והפעלה ידנית; CI שמריץ את הבדיקות הלא־מקוונות ואת ההערכות המהירות לפני כל ריצה בתשלום; גרסאות של הנחיה, מודל ואינדקס יחד, ומה זה „חזרה לאחור” כשאחד מהם הוא מודל אצל ספק; וחלופה מקומית ב־Windows Task Scheduler. בסופו ריצה מתוזמנת תייצר קובץ Markdown ודוח ריצה ב־GitHub בלי שתגעי במקלדת.

מה נלמד בפרק

  • קונפיגורציה וסביבות: מה בקובץ, מה במשתנה סביבה, מה בסוד.
  • GitHub Actions: cron ב־UTC, שעון קיץ, סודות, תוצרים, הפעלה ידנית.
  • CI לפני ריצה: בדיקות לא־מקוונות והערכות מהירות.
  • גרסאות יחד: הנחיה, מודל, אינדקס, סכמה.
  • חזרה לאחור ורעיון הקנרית.
  • מתזמן מקומי כחלופה (Windows Task Scheduler, ועבור Mac cron או launchd); Docker כתיבה אופציונלית.

ידע מקדים

פרק 18 (המדרגות וה־CI), פרק 22 (המעקב), פרק 23 (שומר התקציב). התרגיל דורש מאגר GitHub.

25.1 קונפיגורציה וסביבות

סוג דוגמה איפה למה
קוד הלוגיקה Git משתנה בגרסאות
הגדרה מספר פריטים, שפה, נושאים קובץ בגיט (profile.yaml) שונה בין משתמשות, לא סודי, מגורסן
סביבה שמות מודלים, נתיבים משתני סביבה, או קובץ .env מקומי שונה בין מכונה ל־CI
סוד מפתח API, סיסמת מייל .env מקומי (לא בגיט); GitHub Secrets ב־CI אסור שיהיה בקוד או בלוג
גרסאות הנחיה, מודל, אינדקס versions.json בגיט סעיף 25.4

הכלל: קוד אחד, קונפיגורציה לכל סביבה, סודות מחוץ לגיט. אותו daily_job.py רץ על המחשב שלך (.env), ב־CI (secrets), ובמכולה (משתני סביבה).

25.2 GitHub Actions: המשימה שרצה בלי אדם

ה־workflow בתרגיל (daily.yml) מכיל כל מה שמשימה מתוזמנת צריכה:

on:
  schedule:
    - cron: "0 4 * * *"     # summer: 07:00 Asia/Jerusalem is 04:00 UTC
    - cron: "0 5 * * *"     # winter: 05:00 UTC
  workflow_dispatch:        # the "run it now" button
    inputs: { items: { default: "5" } }

גרסאות של ה־actions. ה־workflow המלא משתמש גם בשלושה actions מוכנים, וכל אחד מוצמד לפי תג של גרסה ראשית. כשכותבים את ה־workflow בודקים כל אחד מול דף ה־releases שלו ב־GitHub; נכון לאוקטובר 2026 אלה הגרסאות הראשיות העדכניות:

ה־action תפקיד גרסה ראשית, נכון לאוקטובר 2026
actions/checkout משיכת הקוד של המאגר v7
astral-sh/setup-uv התקנת uv על המכונה v10
actions/upload-artifact שמירת התוצרים v7

המלכודת של שעון הקיץ. cron ב־GitHub Actions רץ ב־UTC ולא יודע מה זה שעון קיץ. 07:00 בירושלים הוא 04:00 UTC בקיץ (UTC+3) ו־05:00 UTC בחורף (UTC+2). פתרון של שורה אחת ייתן עיתון ב־06:00 או ב־08:00 במחצית השנה. הפתרון בתרגיל: שתי שורות cron, והמשימה בודקת בעצמה (--local-hour 7) אם עכשיו שבע בירושלים; אם לא, היא יוצאת עם קוד 2 בלי לעשות כלום, וה־workflow מתייחס לזה כהצלחה שקטה. cron_for_local_time מחשב את שתי השורות מתוך zoneinfo, לכל אזור זמן.

סודות. GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }} נכנס כמשתנה סביבה; GitHub ממסך אותו בלוגים. בלי הסוד, המדרגה המהירה עדיין רצה (היא לא צריכה מפתח), והמשימה נכשלת מוקדם וברור.

תוצרים. upload-artifact שומר ל־14 יום את שלושת הקבצים של הריצה: העיתון, דוח הריצה וקובץ המעקב (השמות המדויקים בטבלה של סעיף 25.6). זה המקום שבו רואים את העיתון של הבוקר בלי מחשב דולק. if: always() מעלה את התוצרים גם כשהריצה נכשלה: הדוח של ריצה שנכשלה הוא החשוב מכולם.

הפעלה ידנית. workflow_dispatch עם קלט (items) הוא כפתור „הרץ עכשיו” לבדיקה אחרי שינוי.

25.3 CI לפני ריצה בתשלום

הצעד הראשון ב־workflow אחרי ההתקנה הוא uv run pytest -q -m "not judge": המדרגה המהירה של פרק 18, בלי מפתח. אם היא אדומה, המשימה לא רצה, ולא משלמים על ריצה של קוד שבור. ההערכות עם השופט לא רצות כאן (איטיות ובתשלום); הן רצות בלילה אחר, ב־workflow של פרק 18. סדר העבודה: בדיקות, ואז ריצה, ואז תוצרים. ואם הריצה נכשלה, הדוח עולה בכל זאת.

25.4 גרסאות יחד

במערכת רגילה, גרסה היא commit. במערכת מודל, ההתנהגות תלויה בארבעה דברים שמשתנים בנפרד:

רכיב משתנה כש… מי שולט
הנחיה (summarize.v3) עורכים קובץ את
מודל (gemini-3.5-flash-lite) הספק מעדכן, או את מחליפה שניכם
אינדקס (notes-2026-10) מאנדקסים מחדש, או משנים מודל שיכון את
סכמה (schema_version: 1) משנים את ArticleSummary את

versions.json מצהיר על ארבעתם במקום אחד, ו־check_versions משווה אותם למציאות: קובץ ההנחיה קיים? משתני הסביבה של המודלים תואמים? האינדקס נבנה עם מודל השיכון המוצהר? אי־התאמה היא כישלון מוקדם, לא עיתון מוזר: בתרגיל ובפרויקט הבדיקה רצה בתחילת המשימה, לפני כל קריאה למודל, ומחזירה קוד יציאה 5 כשיש בעיה. בצעד 6 ב־README את מפעילה אותה גם ביד, כדי לראות את ההודעה. ואז חזרה לאחור (rollback) היא פעולה מוגדרת: לשחזר את versions.json הקודם (ואת האינדקס שהוא מצביע עליו), לא „לבטל את העריכה של ההנחיה” בלבד, כי ההנחיה החדשה אולי נמדדה מול המודל החדש.

מה שלא נשלט: הספק יכול לשנות את התנהגות המודל מתחת לאותו שם. ההגנה היא ההערכה שרצה בלילה (פרק 18): ציון שיורד בלי שינוי אצלך פירושו שהמודל זז.

25.5 הקנרית

כשמשנים הנחיה או מודל, לא מחליפים את כל העיתון בבת אחת. קנרית (canary) היא ריצה אחת של הגרסה החדשה לצד הישנה: אותם פריטים, שני סיכומים, ההערכה והקוראת משוות, ורק אז מחליפים. בפרויקט זה --versions versions-next.json לריצה ידנית, והשוואת שני הדוחות (פרק 16). עבור מערכת של אדם אחד, זה מספיק; במערכת גדולה, אחוז מהתעבורה.

25.6 המשימה עצמה

daily_job.py הוא מה שה־workflow מריץ, והוא נבנה לרוץ בלי אדם:

תכונה איך
קודי יציאה ברורים 0 הצלחה, 2 דילוג (לא השעה), 3 המודל נכשל על הכול, 4 התקציב נגמר, 5 אי־התאמת גרסאות (לא רץ)
תוצרים תמיד brief-<date>.md ו־run-report.json; הדוח נכתב גם בכישלון
מעקב TracingClient של פרק 22 לכל קריאה; traces.jsonl עולה כתוצר
תקציב BudgetGuard של פרק 23; חריגה כותבת דוח ויוצאת 4
כשל חלקי פריט שנכשל נספר ונרשם; הריצה ממשיכה
הרצה יבשה --dry-run עם FakeClient: אותו קוד, בלי מפתח, ל־CI ולבדיקות
גרסאות קורא versions.json אם קיים; המודל משם

--dry-run הוא מה שמאפשר לבדוק את כל המשימה בלי רשת: הבדיקה מריצה אותה על שלושה פריטים מזויפים ובודקת את הקובץ, את הדוח ואת המעקב. ההרצה האמיתית שונה רק בלקוח.

25.7 Windows Task Scheduler

GitHub Actions דורש מאגר ורשת. על המחשב עצמו, Task Scheduler עושה את אותו דבר, בזמן מקומי (בלי המלכודת של UTC):

schtasks /Create /TN "MorningBrief" /SC DAILY /ST 07:00 /TR "pwsh -File C:\path\to\ai-course\run_daily.ps1" /F
schtasks /Run /TN "MorningBrief"
schtasks /Query /TN "MorningBrief" /V /FO LIST

run_daily.ps1 עובר לתיקיית הפרויקט, מריץ את המשימה עם --env-file .env, ומנתב את הפלט לקובץ לוג יומי. ההבדל מ־CI: המחשב צריך להיות דלוק, והסודות הם .env המקומי. בשביל עיתון אישי זה לגיטימי לגמרי, וזה מה שתעשי אם אין לך מאגר ציבורי.

ב־Mac: המקבילה היא שורת cron או סוכן launchd. שורת ה־crontab הזאת מריצה כל בוקר בשבע את run_daily.sh, שיושב בפרויקט לצד run_daily.ps1:

0 7 * * * cd $HOME/morning-brief && bash run_daily.sh >> out/cron.log 2>&1

cron ב־Mac רץ בזמן מקומי, ולכן אין צורך בתעלול של שעון הקיץ, אבל הוא לא רץ כשהמחשב הנייד ישן; סוכן launchd הוא האפשרות העמידה יותר, כי הוא משלים ריצה שהוחמצה כשהמחשב מתעורר.

25.8 תיבה אופציונלית: Docker

מכולה היא „אותה סביבה בכל מקום”: Python, התלויות והקוד בתמונה אחת, המפתח כמשתנה סביבה בזמן ריצה. ה־Dockerfile בתרגיל הוא עשר שורות עם uv sync --frozen. מתי זה שווה: כשהמשימה רצה על שרת שאינו שלך, או כשצריך גרסת Python מסוימת. מתי לא: לעיתון אישי על המחשב או ב־Actions, uv לבד מספיק.

25.9 בפרויקט

  • אבן דרך 9: daily.yml עם שתי שורות cron, --local-hour, סודות, תוצרים, הפעלה ידנית; versions.json ו־check_versions בתחילת הריצה; קנרית ידנית לפני כל החלפת הנחיה או מודל.
  • ה־README של הפרויקט מסביר את שלוש הדרכים להריץ: ביד, במתזמן מקומי (Task Scheduler ב־Windows, cron או launchd ב־Mac), וב־GitHub Actions.
  • הדוח של ריצה שנכשלה הוא תוצר ראשון במעלה.

סיכום

  • קוד אחד, קונפיגורציה לכל סביבה, סודות מחוץ לגיט, גרסאות בקובץ אחד.
  • cron ב־UTC בלי שעון קיץ: שתי שורות, והמשימה בודקת את השעה המקומית.
  • סודות של המאגר, תוצרים גם בכישלון, כפתור הפעלה ידנית.
  • בדיקות לא־מקוונות לפני כל ריצה בתשלום; השופט בלילה אחר.
  • הנחיה, מודל, אינדקס וסכמה מגורסנים יחד; חזרה לאחור משחזרת את הקובץ; קנרית לפני החלפה.
  • קודי יציאה, דוח תמיד, הרצה יבשה; מתזמן מקומי (Task Scheduler, cron) בזמן מקומי; Docker כשצריך.

טעויות נפוצות

  • שורת cron אחת. העיתון זז בשעה פעמיים בשנה.
  • המפתח בקובץ ה־workflow. סוד של המאגר, או כלום.
  • תוצרים רק בהצלחה. הדוח של הכישלון הוא זה שצריך.
  • ריצה בתשלום בלי בדיקות לפניה. משלמים על קוד שבור.
  • לגרסן רק את ההנחיה. ההנחיה נמדדה מול מודל ואינדקס מסוימים.
  • להחליף מודל בלי קנרית. עיתון שלם ברמה לא ידועה.
  • קוד יציאה אפס תמיד. אף אחד לא יודע שהמשימה דילגה או נכשלה.

שאלות ראיון

  1. איך את פורסת משימת מודל שרצה כל בוקר? GitHub Actions עם cron, שתי שורות בגלל שעון הקיץ והמשימה בודקת את השעה המקומית; המפתח כסוד; בדיקות לא־מקוונות לפני הריצה; תוצרים (העיתון, דוח ריצה, מעקב) גם בכישלון; קודי יציאה ברורים ותקציב. ואותו קוד רץ מקומית עם מתזמן מקומי.
  2. מה הגרסה של מערכת מודל? לא commit בלבד: הנחיה, מודל, אינדקס וסכמה יחד, בקובץ אחד שנבדק מול המציאות בתחילת הריצה. חזרה לאחור משחזרת את הקובץ ואת האינדקס. ומה שהספק משנה מתחת לשם המודל נתפס רק בהערכה שרצה בקביעות. המשך: הציון הלילי ירד ולא שינית כלום. מה הצעד הראשון? לוודא שבאמת לא השתנה כלום אצלך: קובץ הגרסאות, האינדקס והנתונים של ההערכה. רק אז מסיקים שהמודל זז, שומרים את תוצאות ההערכה כראיה, ומחליטים אם לעבור למודל אחר דרך קנרית.
  3. מה המלכודת של cron ב־Actions? הוא ב־UTC ובלי שעון קיץ; שעה מקומית קבועה היא שני זמני UTC בשנה. פתרון: שתי שורות ובדיקה בתוך המשימה, או קבלת סחף של שעה.
  4. איך משנים הנחיה בייצור בלי לשבור את העיתון? גרסה חדשה בקובץ נפרד, ריצת קנרית לצד הישנה על אותם פריטים, השוואה בהערכה ובעין, ואז החלפה של קובץ הגרסאות עם דרך חזרה. המשך: הקנרית טובה יותר בהערכה, אבל הקוראת מעדיפה את הסיכומים הישנים. למי מאמינים? לשתיהן: ההערכה מודדת את מה שהוגדר, והקוראת מצביעה על מה שלא הוגדר. מוסיפים מקרים או מדד שתופסים את ההעדפה שלה, ורק אז מחליפים.

  • חמישה סוגים: קוד בגיט; הגדרה בקובץ מגורסן; סביבה במשתני סביבה; סוד בקובץ הסביבה המקומי או בסודות של GitHub; גרסאות בקובץ אחד.
  • cron רץ ב־UTC בלי שעון קיץ. 07:00 בירושלים הוא 04:00 UTC בקיץ ו־05:00 בחורף: שתי שורות, והמשימה בודקת את השעה המקומית.
  • ה־workflow: סודות, העלאת תוצרים גם בכישלון, כפתור הפעלה ידנית; בדיקות לפני הריצה.
  • קובץ הגרסאות: הנחיה, מודל, אינדקס, סכמה; בדיקה מול המציאות לפני הריצה; חזרה לאחור משחזרת את הקובץ ואת האינדקס.
  • קנרית לפני החלפה. קודי יציאה: 0 הצלחה, 2 דילוג, 3 כשל, 4 תקציב, 5 גרסאות. דוח תמיד. הרצה יבשה.
  • מתזמן מקומי: זמן מקומי, קובץ הסביבה, מחשב דלוק (Task Scheduler ב־Windows; cron או launchd ב־Mac). Docker: כשהשרת לא שלך.
  • שאלה פתוחה: ___
cron      cron_for_local_time(7, 0) -> summer "0 4 * * *", winter "0 5 * * *";  is_local_hour(now_utc, 7)
job       python -m ch25.daily_job --out out --items 5 [--dry-run] [--local-hour 7] [--versions versions.json]   exit 0/2/3/4
versions  load_versions(path) -> Versions; check_versions(v, prompts_dir=, env=, index_metadata=) -> [problems]
actions   .github/workflows/daily.yml: schedule x2 + workflow_dispatch; secrets.GEMINI_API_KEY; pytest first; upload-artifact if: always()
windows   schtasks /Create /TN "MorningBrief" /SC DAILY /ST 07:00 /TR "pwsh -File ...\run_daily.ps1" /F
docker    docker build -t morning-brief . ; docker run --rm -e GEMINI_API_KEY -v "$PWD/out:/app/out" morning-brief

תרגיל

מטרה: לבנות את המשימה היומית עם קודי יציאה, מעקב ותקציב; לפרוס אותה ב־GitHub Actions עם שתי שורות cron, סודות, תוצרים והפעלה ידנית; לגרסן הנחיה, מודל ואינדקס יחד; ולהריץ אותה גם מ־Task Scheduler. זמן: יום לימוד אחד (יום 49), כ־70 דקות בנייה, ועוד המתנה לריצה המתוזמנת. ידע מקדים: הפרק, פרקים 18, 22 ו־23, מאגר GitHub ומפתח API.

הצעדים, קוד ההתחלה, הרמזים והפתרון נמצאים ב־ exercises/ch25-deployment-scheduling/README.md.

קריטריון סיום:

  • ריצה ידנית (workflow_dispatch) ירוקה ב־GitHub עם תוצר שמכיל את העיתון, הדוח והמעקב.
  • הריצה המתוזמנת הבאה ייצרה תוצר בעצמה (או דילגה עם קוד 2 בשעה הלא נכונה, ורואים את זה בלוג).
  • versions.json במאגר, ו־check_versions נכשל כשמשנים משתנה סביבה בכוונה.
  • ארבע הבדיקות עוברות בלי רשת; המשימה רשומה גם ב־Task Scheduler ורצה פעם אחת.

העשרה אופציונלית

  • התיעוד של GitHub Actions על schedule (כולל האזהרה שריצות מתוזמנות עלולות להתעכב בעומס) ועל workflow_dispatch.
  • „The Twelve-Factor App”: קונפיגורציה בסביבה, תהליכים חסרי מצב, לוגים כזרמים.
  • uv ו־Docker: uv sync --frozen בתמונה, והסבר על --no-sync בזמן ריצה.
