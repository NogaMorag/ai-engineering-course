## "Delivery", in plain words

The newsletter agent produces one issue every morning. "Delivery" is simply *how that issue reaches
you*. The choices are:

- **A file on disk.** The program writes `brief-2026-10-04.md` and `.html` into a folder. Zero
  setup, always on. This is the default and always happens.
- **Email.** The program also sends the HTML issue to your inbox. It logs into Gmail's outgoing mail
  server (SMTP) with an *app password*: a 16-character password that Google issues for a single
  program, so your real password is never in the code. Requires 2-Step Verification on the Google
  account. Free.
- **Telegram.** The program posts the issue to a chat with a bot you create in two minutes. Also
  free, no 2-Step Verification needed. Optional alternative.

The project builds delivery as a small pluggable module, so changing your mind later costs about
thirty lines of code.

## Consequences you will notice in the book

1. Every command is PowerShell. No `brew`, no `source`, no `~/`; instead `winget`, `$env:`, `$HOME`.
2. One extra Windows-only step on Day 2: setting `PYTHONUTF8=1` so Hebrew text prints correctly in
   the terminal. Without it Python on Windows may print question marks or raise an encoding error.
3. Model names live only in `.env` (`MODEL_FAST`, `MODEL_SMART`). Google released three new Flash
   models in the three months before this plan was written; the book teaches you to check the
   models page rather than memorize names.
4. The free tier has per-minute limits. Exercises that fire many requests include a tiny throttle,
   which is also how real services behave under a rate limit.
5. Free-tier prompts may be used by Google to improve its products. Fine for the course, which uses
   public data only. For the newsletter, which contains your interests profile, you can either
   accept that or prepay $5 once for Tier 1, where content is not used for training. The book shows
   both and leaves the choice to you.

## Part 3 implementation notes (Chapters 7–11, written 2026-10-03)

- **Schedule D14–D19 wording aligned to the Gemini Interactions API.** The Stage 1 schedule still used
  `messages.parse()`, `tool_use`/`tool_result` and `get_final_message()` from the original draft. Replaced
  with `response_format`, `function_call`/`function_result` and streaming events. Day numbers unchanged.
- **Ch 9 exercise uses the three Ch 8 articles, not five**, and the `ArticleSummary` schema drops the
  `entities` field in favour of `is_article` (the escape hatch the chapter teaches). Fewer live calls on the
  free tier; same learning goals.
- **Ch 11 owns the retry policy.** On the Interactions path the SDK defaults to 3 attempts (one request plus two retries; `HttpRetryOptions.attempts` overrides it);
  the course disables it (`attempts=1`) and implements backoff with full jitter plus a total deadline in
  `with_retries`, so the "do not double-retry" lesson is explicit in code.
- **Interactions-API errors live in a private SDK module** with no public base class; the client converts
  by duck typing on `status_code` at a single boundary. Recorded here so a future SDK that exports the
  classes can replace `classify` without touching callers.
- **Checkpoint 2 CLI exposes exit codes** (0 / 2 not-article / 3 model failure / 4 fetch failure) so the
  Part 7 scheduler can branch on them without parsing output.
