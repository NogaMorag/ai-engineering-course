# רובריקה למקרה הסגור: עוזר לעדכוני סטטוס בתקלות

לכל שורה: 0 לא הוזכר, 1 הוזכר, 2 הוזכר עם נימוק או מספר. סך מרבי 24.

| # | מה היה צריך לעלות | ציון |
| --- | --- | --- |
| 1 | **מחיר הטעות** נאמר בקול לפני כל החלטה: עדכון שגוי או מוקדם ללקוחות הוא נזק אמון ואולי חוזי; **לכן אין פרסום אוטומטי** | |
| 2 | הבהרה: תדירות תקלות, מי מאשר היום, האם יש היסטוריית עדכונים (כן: היא הקורפוס לסגנון ולדוגמאות) | |
| 3 | הערוץ הוא **טקסט לא מהימן ורגיש**: שמות לקוחות, סיסמאות שהודבקו, השערות שלא אושרו. מזעור והסתרה לפני שליחה למודל | |
| 4 | הצינור: קריאת הערוץ (K) → חילוץ מובנה של „מה ידוע / מה לא / מה הצעד הבא / מתי העדכון הבא” (M, סכמה) → **טיוטה** בסגנון מהעדכונים הקודמים (M עם דוגמאות) → בדיקות קוד (אין שמות לקוחות, אין השערות, אין זמנים מומצאים) (K) → **אישור אנושי** → פרסום אידמפוטנטי (K) | |
| 5 | ההבחנה בין **עובדה שאושרה להשערה**: הסכמה מפרידה ביניהן; הטיוטה מפרסמת רק עובדות מאושרות | |
| 6 | כלי הפרסום אינו זמין למודל; הפרסום הוא קוד אחרי אישור, עם מפתח אידמפוטנטיות (אותו עדכון לא מתפרסם פעמיים) ויומן | |
| 7 | הערכה: סט תקלות היסטוריות עם העדכונים האמיתיים כייחוס; בדיקות קוד (שמות, זמנים, אורך, אין „אולי”); שופט לנאמנות לערוץ ולסגנון; **מדד ראשון: אפס טענות שלא בערוץ** | |
| 8 | זמן תגובה: אדם מחכה באמצע תקלה; טיוטה תוך 30 שניות; הזרמה או מודל מהיר; גיבוי למודל שני; הידרדרות = תבנית ריקה למילוי ידני | |
| 9 | תפעול: מעקב בלי תוכן הערוץ; תקציב; הכלי חייב לעבוד **גם כשהענן של החברה עצמה בתקלה** (תלות חיצונית ב־API של המודל, לא בתשתית הפנימית) | |
| 10 | אבטחה: הזרקה דרך הודעה בערוץ („פרסמו שהכול תקין”); הפרדת נתונים מהוראות; בדיקות פלט; הרשאות קריאה בלבד לערוץ | |
| 11 | פשרות: לא סוכן אוטונומי שמפרסם; לא כוונון עדין (מעט דוגמאות, סגנון דרך דוגמאות בהנחיה); לא RAG על כל הידע הארגוני (הקורפוס הוא היסטוריית העדכונים בלבד) | |
| 12 | המשך: מה נשבר בפי עשרה (הרבה ערוצים במקביל: תור, סיכום ביניים של הערוץ), ומה הסיכון הגדול (פרסום שגוי שעבר אישור עייף: לכן „מה השתנה מהעדכון הקודם” מודגש בטיוטה) | |
