# פרק 11: לקוחות עמידים וניידות בין ספקים

כל הקוד שכתבת עד כה הניח שהרשת עובדת, שהשרת עונה, ושאף אחד לא חרג ממכסה. בייצור אף אחת מההנחות
האלה לא מחזיקה לאורך זמן. בקשה נכשלת בחמישה־שישה אופנים שונים, וכל אחד דורש תגובה אחרת: יש שגיאות
שכדאי לנסות שוב אחריהן, יש כאלה שניסיון חוזר רק יחזור על הטעות, ויש כאלה שעולות כסף גם כשנראה
שנכשלו. הפרק הזה בונה את השכבה שבין היישום לבין ספק המודל: סיווג שגיאות, ניסיונות חוזרים עם המתנה
חכמה, זמן קצוב, הזרמה, והתמודדות עם מגבלות קצב. ואז הוא עוטף הכול בממשק אחד, `LLMClient`, כך
ששאר הקורס והפרויקט לא יכירו את Gemini בכלל, ויוכלו לעבור לספק אחר בקובץ אחד. בסופו, נקודת ביקורת
2: כלי שורת פקודה שמסכם כל כתובת, בנוי מכל מה שלמדת בחלק ג.

## מה נלמד בפרק

- מה משתבש בזמן ריצה, ואילו כשלים ראוי לנסות שוב.
- סיווג שגיאות להיררכיה שלנו, ולמה לא תופסים את השגיאות של הספרייה ישירות.
- ניסיונות חוזרים: גידול מעריכי, אקראיות, גבול ניסיונות, גבול זמן כולל, ולמה לא פעמיים.
- זמן קצוב, ומה הוא לא אומר על החיוב.
- הזרמה: אירועים, זמן לטוקן הראשון מול זמן כולל, ומתי לא להזרים.
- מגבלות קצב ומקביליות.
- המתאם (adapter): `LLMClient`, `GeminiClient`, `FakeClient`, ומה דולף דרכו.
- נקודת ביקורת 2: מסכם הכתבות.

## ידע מקדים

פרקים 7 עד 10. התרגיל קורא ל־API; החלק האופציונלי דורש ספק שני או Ollama.

## 11.1 מה משתבש, ומה עושים עם זה

הטבלה הזאת היא לב הפרק. כל השאר הוא מימוש שלה.

| מה קרה | קוד | סיבה טיפוסית | לנסות שוב? |
| --- | --- | --- | --- |
| בקשה שגויה | 400 | סכמה לא חוקית, פרמטר לא קיים, הנחיה ריקה | לא. אותה בקשה תיכשל שוב |
| אימות | 401, 403 | מפתח חסר, שגוי או ללא הרשאה | לא. לתקן את הסביבה |
| לא נמצא | 404 | שם מודל שגוי | לא |
| חריגה ממכסה | 429 | יותר מדי בקשות או טוקנים לדקה; מכסה יומית | כן, אחרי המתנה. מכסה יומית: לא |
| שגיאת שרת | 500 ואילך | תקלה אצל הספק, עומס | כן, אחרי המתנה |
| זמן קצוב, ניתוק | אין קוד | רשת, שרת איטי, בקשה גדולה | כן, אחרי המתנה. אולי כבר חויבת |
| פלט קטוע | סטטוס `incomplete` | `max_output_tokens` נמוך | לא כניסיון חוזר; להגדיל את המגבלה |

שני עקרונות יוצאים מהטבלה. הראשון: **ניסיון חוזר הוא תרופה לכשל זמני בלבד.** 400 ו־401 לא
יתוקנו מעצמם; לנסות שוב רק מבזבז זמן ומסתיר את הבאג. השני: **כשל לא אומר שלא שילמת.** בקשה שקיבלה
זמן קצוב אצלך יכולה להסתיים בהצלחה בשרת, והטוקנים שנוצרו מחויבים. ניסיון חוזר הוא בקשה חדשה, עם
חיוב חדש.

## 11.2 סיווג שגיאות להיררכיה שלנו

ספריית ה־SDK זורקת חריגות משלה, אבל במהדורה הנוכחית המחלקות של ממשק ה־Interactions יושבות במודול
פרטי, ואי אפשר לייבא אותן בצורה יציבה. גם אם היה אפשר, לא היינו רוצים: אם היישום תופס
`google.genai.SomethingError`, היישום יודע על Gemini, ועברנו ספק ישברו עשרים קבצים. הפתרון הוא
היררכיה שלנו, והמרה בנקודה אחת:

<div dir="ltr" align="left">

```python
class LLMError(Exception):
    retryable = False

class LLMRateLimited(LLMError):
    retryable = True

class LLMUnavailable(LLMError):      # 5xx, connection problems, timeouts
    retryable = True

class LLMBadRequest(LLMError):       # 4xx other than 429
    pass

class LLMTruncated(LLMError):        # status == "incomplete"
    pass


def classify(exc: BaseException) -> LLMError:
    status = getattr(exc, "status_code", None)
    if status == 429:
        return LLMRateLimited(str(exc), status_code=status, cause=exc)
    if isinstance(status, int) and status >= 500:
        return LLMUnavailable(str(exc), status_code=status, cause=exc)
    if isinstance(status, int) and 400 <= status < 500:
        return LLMBadRequest(str(exc), status_code=status, cause=exc)
    if isinstance(exc, TimeoutError | ConnectionError) or "Timeout" in type(exc).__name__:
        return LLMUnavailable(str(exc), cause=exc)
    return LLMError(str(exc), cause=exc)
```

</div>

הטריק נקרא טיפוס ברווז (duck typing): במקום לשאול „מאיזו מחלקה אתה”, שואלים „יש לך `status_code`?”.
לחריגות ה־HTTP של כל ספק סביר יש. ההמרה קורית במקום אחד, בתוך `GeminiClient`, עם `except
Exception` רחב שמיד זורק מחדש כשגיאה שלנו (`raise classify(exc) from exc`). ה־`from` שומר את
החריגה המקורית בשרשרת, כדי שבעקבות (traceback) עדיין יהיה אפשר לראות מה הספרייה אמרה. כל שאר
הקוד תופס רק `LLMError` ובנותיה.

## 11.3 ניסיונות חוזרים שלא מזיקים

ניסיון חוזר נאיבי, „אם נכשל, נסה שוב מיד”, הוא בעיה: אם הספק עמוס, אלף לקוחות שמנסים שוב באותה
שנייה מחמירים את העומס. הדפוס הסטנדרטי הוא גידול מעריכי עם אקראיות (exponential backoff with
jitter):

| ניסיון | תקרת המתנה | המתנה בפועל |
| --- | --- | --- |
| 1 נכשל | 1 שנייה | אקראי בין 0 ל־1 |
| 2 נכשל | 2 שניות | אקראי בין 0 ל־2 |
| 3 נכשל | 4 שניות | אקראי בין 0 ל־4 |
| 4 נכשל | 8 שניות, עד תקרה קבועה | אקראי בין 0 ל־8 |

האקראיות („אקראי בין 0 לתקרה”, הצורה שנקראת full jitter) מפזרת את הלקוחות בזמן. התקרה הקבועה
(למשל 20 שניות) מונעת המתנות של דקות. ולצידם שני גבולות שחייבים להיות:

- **גבול ניסיונות.** ארבעה ניסיונות הם ברירת מחדל סבירה.
- **גבול זמן כולל (deadline).** אם ההמתנה הבאה תחרוג מתקציב של, נניח, 90 שניות, מפסיקים. בלי
  זה, משתמשת מחכה שתי דקות לתשובה שלא תגיע.

<div dir="ltr" align="left">

```python
def with_retries(operation, policy, *, sleep=time.sleep, clock=time.monotonic, rng=None):
    rng = rng or random.Random()
    started = clock()
    for attempt in range(1, policy.max_attempts + 1):
        try:
            completion = operation()
        except LLMError as err:
            if not err.retryable or attempt == policy.max_attempts:
                raise
            wait = policy.delay(attempt, rng)
            if clock() - started + wait > policy.total_deadline_s:
                raise LLMUnavailable("deadline exhausted") from err
            sleep(wait)
            continue
        completion.attempts = attempt
        return completion
```

</div>

שימי לב ש־`sleep`, `clock` ו־`rng` הם פרמטרים. בבדיקות מזריקים שעון מזויף ושינה שלא ישנה, וכל
מדיניות הניסיונות נבדקת באלפית שנייה, בלי רשת ובלי המתנה. זה לא פינוק: קוד ניסיונות חוזרים שלא
נבדק הוא בדיוק הקוד שמתגלה כשגוי בשלוש בלילה.

**לא פעמיים.** ל־SDK יש מנגנון ניסיונות משלו, ובברירת המחדל הוא פעיל: עד חמישה ניסיונות על 408,
429 ו־5xx, עם המתנה מעריכית. אם מוסיפים מעליו את `with_retries` בלי לדעת, מקבלים עשרים ניסיונות
וזמן המתנה שאי אפשר להסביר. בקורס מכבים את מנגנון הספרייה (`attempts=1`, שפירושו ניסיון אחד
כולל המקורי) ומנהלים את המדיניות במקום אחד, שלנו. הכלל: **רכיב אחד הוא הבעלים של הניסיונות
החוזרים.** אם ספרייה חיצונית עושה את זה טוב, משתמשים בה ולא כותבים מעליה; אם כותבים, מכבים אותה.

**אידמפוטנטיות.** ניסיון חוזר בטוח רק לפעולות שאפשר לחזור עליהן בלי נזק. קריאה למודל שמייצרת
טקסט היא כזאת (למעט העלות). סבב בלולאת כלים שכבר הריץ כלי עם תופעת לוואי, לא. לכן בפרויקט,
הניסיונות החוזרים חיים ב־`complete`, לא סביב לולאת הסוכן.

## 11.4 זמן קצוב

בלי זמן קצוב (timeout), בקשה שנתקעה תחכה לנצח, והלולאה שמסביבה איתה. הגדרה אחת ברמת הלקוח:

<div dir="ltr" align="left">

```python
from google.genai import types

http_options = types.HttpOptions(
    timeout=60_000,                                    # milliseconds
    retry_options=types.HttpRetryOptions(attempts=1),  # one attempt: we own the retry policy
)
client = genai.Client(http_options=http_options)
```

</div>

היחידה היא אלפיות שנייה, וזו מלכודת: `timeout=60` הוא שישים אלפיות. חישוב שכדאי לעשות פעם אחת
ולזכור: **הזמן המרבי לקריאה הוא זמן קצוב כפול מספר ניסיונות, ועוד סכום ההמתנות.** עם 60 שניות,
ארבעה ניסיונות והמתנות של עד 1, 2 ו־4 שניות, זה עד 247 שניות. אם זה יותר ממה שהמשתמשת תסבול,
מקצרים את הזמן הקצוב או את מספר הניסיונות, או מעבירים את העבודה לרקע. בפרויקט, שרץ בלילה בלי
משתמשת שמחכה, התקציב נדיב; בכלי שורת הפקודה של נקודת הביקורת, פחות.

ושוב העובדה הלא נעימה: זמן קצוב בצד הלקוח לא מבטל את הבקשה בשרת. אם המודל סיים אחרי 61 שניות,
הטוקנים חויבו, והתשובה נזרקה.

## 11.5 הזרמה

במצב הרגיל, הלקוח מחכה עד שהמודל סיים ומקבל את הכול. ב„הזרמה” (streaming) השרת שולח חלקים
(deltas) בזמן שהם נוצרים. למדידה יש שני מספרים שונים:

- **זמן לטוקן הראשון** (time to first token, TTFT): כמה מהר המשתמשת רואה שמשהו קורה. בהזרמה זה
  בדרך כלל פחות משנייה.
- **זמן כולל:** כמה זמן עד שהתשובה שלמה. הזרמה לא מקצרת אותו; המודל מייצר באותו קצב.

<div dir="ltr" align="left">

```python
for event in client.interactions.create(model=model, input=prompt, stream=True):
    if event.type == "step.delta" and event.delta.type == "text":
        print(event.delta.text, end="", flush=True)
    elif event.type == "interaction.completed":
        usage = event.interaction.usage
```

</div>

האירועים שמגיעים: `interaction.created`, `step.start`, `step.delta` (עם `delta.type` שהוא
`text` לטקסט), `step.stop`, `interaction.completed` (ובו השימוש והסטטוס), ו־`error`. את השימוש
בטוקנים מקבלים רק בסוף.

מתי להזרים? כשיש אדם שמחכה: צ׳אט, עוזר בעורך, כלי אינטראקטיבי. מתי לא? כשהקוד הוא שממשיך:
צינור לילי, פלט מובנה (JSON חלקי לא שווה כלום עד שהוא שלם), או קריאות שהתוצאה שלהן נשמרת ולא
מוצגת. בפרויקט אין משתמשת שמחכה, ולכן אין הזרמה; בלקוח היא קיימת כדי שתכירי אותה, ובכלי שורת
הפקודה אפשר להפעיל אותה. עוד כלל: הזרמה לא מנוסה שוב באמצע. אם הזרם נשבר אחרי מחצית התשובה, אי
אפשר „להמשיך מאותו מקום”; מתחילים מחדש, ומה שכבר הודפס צריך להימחק או להתווסף אליו הסבר.

## 11.6 מגבלות קצב ומקביליות

השכבה החינמית מגבילה בקשות לדקה, טוקנים לדקה, ובקשות ליום, והמספרים המדויקים מופיעים רק
ב־AI Studio ומשתנים. כמה כללים שעובדים בכל מדרגה:

- **429 הוא מידע, לא כישלון.** ההמתנה המעריכית מטפלת בו; אם מגיעה כותרת `Retry-After` מכבדים
  אותה. מכסה *יומית* שנגמרה היא עניין אחר: לא מנסים שוב, מדווחים ומסיימים.
- **מקביליות מבוקרת.** עשרים כתבות במקביל הן עשרים בקשות באותה שנייה. סמפור של שתיים או שלוש
  בקשות בו־זמנית, או פשוט לולאה סדרתית עם המתנה קצרה, מספיקים לפרויקט. בחלק ח נדבר על תור.
- **פחות בקשות.** דה־דופליקציה לפני סיכום (חלק ד) ושמירה במטמון של תשובות זהות (חלק ח) חוסכות
  יותר מכל כוונון של ניסיונות חוזרים.
- **לרשום שימוש.** כל קריאה רושמת טוקנים ומספר ניסיונות. בלי זה, „למה קיבלנו 429” היא שאלה בלי
  תשובה.

## 11.7 המתאם: ממשק אחד, ספק אחד בקובץ אחד

כל מה שלמעלה מתכנס לקובץ אחד, `llm_client.py`, ולשלוש מחלקות:

<div dir="ltr" align="left">

```python
class LLMClient(Protocol):
    def complete(self, prompt, *, system=None, max_output_tokens=1024, temperature=0.2, response_format=None) -> Completion: ...
    def stream(self, prompt, *, system=None, max_output_tokens=1024) -> Iterator[str]: ...


class GeminiClient:      # the real one: timeouts, classify, with_retries, streaming
    ...


@dataclass
class FakeClient:        # scripted answers (or exceptions) for tests; never touches the network
    script: list[str | Exception]
```

</div>

`Protocol` (פרק 7) מגדיר את החוזה בלי ירושה. `GeminiClient` מממש אותו מול Gemini. `FakeClient`
מממש אותו מתוך תסריט: רשימה של תשובות או חריגות, כדי שבדיקה תוכל לומר „הקריאה הראשונה מחזירה
429, השנייה JSON תקין”. כל שאר הקורס מקבל `LLMClient` כפרמטר ולא מייבא `google.genai` לעולם.

מה המתאם מסתיר היטב: אימות, ניסיונות חוזרים, זמן קצוב, הזרמה, שגיאות. מה **דולף** דרכו, וכדאי
לדעת מראש:

| דולף | למה | מה עושים |
| --- | --- | --- |
| שמות מודלים | לכל ספק שמות משלו | משתני סביבה, לא מחרוזות בקוד |
| ניב הסכמות | ספקים תומכים בתת־קבוצות שונות של JSON Schema | סכמות שטוחות, בלי הפניות |
| ספירת טוקנים | טוקנייזרים שונים, מחירים שונים | למדוד אצל כל ספק מחדש |
| פורמט הכלים | שמות שדות שונים לקריאה ולתוצאה | מתאם נפרד ללולאת הכלים, אם צריך |
| איכות | אותה הנחיה, תוצאות שונות | ההערכות של חלק ה רצות מחדש אחרי החלפת ספק |

ניידות היא לא „החלפה בלי מחשבה”; היא „החלפה בקובץ אחד, ואז הרצת ההערכות”.

**ספק שני, אופציונלי.** ל־Gemini יש נקודת קצה תואמת OpenAI, ולאותו מפתח. עם חבילת `openai`
אפשר לכתוב מימוש שני של `LLMClient` בעשרים שורות, או להצביע על Ollama מקומי בשינוי כתובת:

<div dir="ltr" align="left">

```python
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["GEMINI_API_KEY"],
    base_url="https://generativelanguage.googleapis.com/v1beta/openai/",
)
response = client.chat.completions.create(
    model="gemini-3.5-flash-lite",
    messages=[{"role": "user", "content": prompt}],
    max_tokens=300,
)
text = response.choices[0].message.content
```

</div>

ל־Ollama: `base_url="http://localhost:11434/v1"`, `api_key="ollama"`, ושם מודל מקומי. העניין
בתרגיל האופציונלי הוא לא הקוד אלא ההשוואה: אותה הנחיה, אותה סכמה, ולראות מה השתנה.

## 11.8 המינימום של תצפיתיות

חלק ח יעסוק במעקב (tracing) ברצינות. כבר עכשיו, שלושה דברים נרשמים בכל קריאה, כי בלעדיהם אי
אפשר לדבג כלום:

- מספר הניסיונות ואילו שגיאות היו בדרך (`on_retry` בלקוח מדפיס שורה).
- זמן התגובה.
- טוקנים בכניסה וביציאה.

`Completion` מחזיר את כולם. בפרויקט הם ייכתבו לטבלה; בכלי שורת הפקודה הם מודפסים לשגיאה
הסטנדרטית (stderr), כדי לא לערבב אותם בפלט.

## סיכום

- כשל הוא קטגוריה, לא אירוע: 4xx לא מנסים שוב, 429 ו־5xx וזמן קצוב מנסים, קטוע מגדילים.
- ממירים שגיאות ספק להיררכיה שלנו בנקודה אחת, לפי `status_code`.
- ניסיונות חוזרים: גידול מעריכי עם אקראיות, גבול ניסיונות, גבול זמן כולל, רק לכשלים זמניים, ורק
  רכיב אחד הוא הבעלים. מנגנון הספרייה כבוי.
- זמן קצוב באלפיות שנייה; הזמן המרבי הוא זמן קצוב כפול ניסיונות ועוד המתנות; כשל לא אומר שלא
  חויבת.
- הזרמה משפרת זמן לטוקן ראשון, לא זמן כולל; לא לפלט מובנה ולא לצינורות; לא מנוסה שוב באמצע.
- `LLMClient` הוא הגבול: `GeminiClient` מולו, `FakeClient` לבדיקות, ושאר הקוד לא מכיר ספק.

## מונחים לזכור

| מונח בעברית | באנגלית | במשפט אחד |
| --- | --- | --- |
| כשל זמני | transient failure | כשל שסביר שייעלם בניסיון הבא: 429, 5xx, זמן קצוב |
| ניסיון חוזר | retry | בקשה חדשה אחרי כשל זמני, עם המתנה |
| גידול מעריכי עם אקראיות | exponential backoff with jitter | המתנה שמוכפלת בכל כשל, עם פיזור אקראי |
| גבול זמן כולל | deadline | התקציב לכל הניסיונות יחד |
| זמן קצוב | timeout | כמה זמן מחכים לבקשה אחת לפני שמוותרים עליה |
| אידמפוטנטיות | idempotency | אפשר לחזור על הפעולה בלי נזק נוסף |
| הזרמה | streaming | קבלת התשובה בחלקים בזמן היצירה |
| זמן לטוקן ראשון | time to first token (TTFT) | כמה זמן עד שמשהו מופיע |
| מגבלת קצב | rate limit | תקרת בקשות או טוקנים ליחידת זמן; 429 |
| מתאם | adapter | שכבה שמסתירה ספק מאחורי ממשק שלנו |
| טיפוס ברווז | duck typing | לבדוק תכונה (`status_code`) במקום מחלקה |

## טעויות נפוצות

- **לנסות שוב על 400.** הבקשה שגויה; הניסיון החוזר מסתיר את הבאג ומבזבז זמן.
- **ניסיונות חוזרים בשתי שכבות.** הספרייה כבר מנסה חמש פעמים כברירת מחדל. אחד הבעלים, לא שניים.
- **`timeout=60` וחשיבה בשניות.** היחידה היא אלפיות שנייה.
- **להניח שזמן קצוב מבטל חיוב.** השרת ממשיך; הטוקנים נספרים.
- **לתפוס `Exception` בכל מקום.** רק בגבול ההמרה, וממנו החוצה רק `LLMError`.
- **להזרים פלט מובנה.** JSON חלקי לא שימושי; מחכים לסוף.
- **ליבא את ספריית הספק מחוץ ללקוח.** זה מה שהופך „להחליף ספק” לפרויקט של שבוע.

## שאלות ראיון

1. **אילו שגיאות תנסי שוב, ואיך?** רק כשלים זמניים: 429, 5xx, זמן קצוב וניתוק. עם המתנה מעריכית
   ואקראיות, גבול ניסיונות, וגבול זמן כולל. 4xx אחרים לא; פלט קטוע מקבל מגבלה גדולה יותר. ורק רכיב
   אחד הוא הבעלים של המדיניות, כדי לא לנסות פעמיים בשתי שכבות.
2. **מה ההבדל בין זמן לטוקן ראשון לזמן כולל, ומתי הזרמה עוזרת?** זמן לטוקן ראשון הוא מתי המשתמשת
   רואה משהו; זמן כולל הוא מתי התשובה שלמה. הזרמה מקצרת את הראשון בלבד. היא עוזרת כשאדם מחכה,
   ולא בצינורות, בפלט מובנה או בקריאות שתוצאתן נשמרת.
3. **איך בונים לקוח שאפשר להחליף בו ספק?** ממשק שלנו (`Protocol`) עם `complete` ו־`stream`; מימוש
   לכל ספק שממיר שגיאות להיררכיה שלנו בנקודה אחת; מימוש מזויף לבדיקות; שאר הקוד לא מייבא ספרייה
   של ספק. ומודעות למה שדולף: שמות מודלים, ניב סכמות, ספירת טוקנים, ואיכות, שדורשת הרצת הערכות
   מחדש.
4. **למה זמן קצוב לא מבטיח שלא שילמת?** כי הוא מתרחש אצלי. השרת ממשיך לייצר, מסיים, ומחייב. ניסיון
   חוזר הוא בקשה שנייה, בתשלום שני. לכן מתכננים את התקציב מראש: זמן קצוב כפול ניסיונות ועוד
   המתנות.
