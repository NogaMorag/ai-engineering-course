# פרק 19: תהליכי עבודה מול סוכנים, והלולאה ביד

„סוכן” (agent) היא המילה הכי עמוסה בתחום, ולכן הפרק מתחיל בהגדרה תפעולית: **סוכן הוא מערכת שבה
המודל מחליט על זרימת הבקרה**, איזה כלי להפעיל, האם להמשיך, מתי לעצור. ב„תהליך עבודה” (workflow)
הקוד מחליט על הזרימה, והמודל ממלא צעדים בתוכה. רוב מה שנקרא סוכן בשיווק הוא תהליך עבודה, וזה טוב:
תהליך עבודה צפוי, זול, וניתן לבדיקה. הפרק מלמד חמישה דפוסים של תהליכי עבודה, מתי אוטונומיה באמת
מוצדקת, ואת הלולאה של סוכן, מצב, כלים, תקציבים, סיבות עצירה ומעקב, כתובה ביד, כי זה מה שכל
ספרייה מסתירה. בסופו יהיה לך סוכן מחקר שעונה על שאלה עם מקורות בשישה צעדים לכל היותר, ועוצר
בכבוד כשהתקציב נגמר.

## מה נלמד בפרק

- ההגדרה התפעולית, ולמה ההבחנה חשובה לעלות, לצפיות ולבדיקות.
- חמישה דפוסים: שרשור, ניתוב, מקבול, מתזמר ועובדים, מעריך ומשפר.
- ארבעת הקריטריונים לאוטונומיה.
- הלולאה: מצב, כלים, תקציבים, סיבות עצירה, מעקב.
- תכנון כטיוטה, לא כחוזה.
- עיצוב כלים לסוכנים.

## ידע מקדים

פרק 10 (קריאה לכלים והמשגר), פרק 11 (הלקוח) ופרק 7 (היסטוריה מפורשת). התרגיל קורא ל־API.

## 19.1 ההגדרה התפעולית

| | תהליך עבודה | סוכן |
| --- | --- | --- |
| מי מחליט מה הצעד הבא | הקוד | המודל |
| מספר הקריאות | ידוע מראש | משתנה, בתוך תקציב |
| עלות וזמן | צפויים | חסומים מלמעלה בלבד |
| בדיקות | כל צעד בנפרד | כל הלולאה, עם תסריטים |
| כשל טיפוסי | צעד אחד נכשל | לולאה אינסופית, ארגומנטים שגויים, עלות בורחת |
| דוגמה בפרויקט | כל הצינור: איסוף, סיכום, דירוג, הרכבה, שליחה | שלב המחקר בלבד |

הכלל: **הכי פחות אוטונומיה שעובדת.** אם הקוד יודע מה הצעד הבא, הוא יחליט, לא המודל.

## 19.2 חמישה דפוסים של תהליכי עבודה

| דפוס | מה | מתי | בקורס |
| --- | --- | --- | --- |
| שרשור (prompt chaining) | פלט של קריאה הוא קלט של הבאה, עם בדיקה בין לבין | משימה שמתפרקת לשלבים ברורים | סיכום ואז דירוג (אבן דרך 2) |
| ניתוב (routing) | סיווג קודם, ואז הנחיה מתאימה לסוג | קלטים שונים דורשים טיפול שונה | `summarize_routed`: סוג הכתבה קובע את ההנחיה |
| מקבול (parallelization) | אותה פעולה על הרבה פריטים בו־זמנית, או כמה זוויות על אותו פריט | הרבה פריטים עצמאיים | `parallel_map` עם סמפור |
| מתזמר ועובדים (orchestrator–workers) | מודל מפרק משימה לתת־משימות, עובדים מבצעים, מאחדים | כשהפירוק עצמו דורש שיפוט | מחקר של כמה סיפורים במקביל (חלק ח) |
| מעריך ומשפר (evaluator–optimizer) | מודל מייצר, מודל שני מבקר לפי קריטריונים, חוזרים עד שעובר | כשיש קריטריון ברור ושווה את הכפל | ניסיון התיקון של פרק 9 הוא גרסה של זה |

שני הדפוסים שהתרגיל מממש:

**ניתוב.** קריאה מובנית קצרה מסווגת את הכתבה לאחד מחמישה סוגים (פרק 9, enum), ומילון ממפה סוג
להנחיה. סיכום של פוסטמורטם צריך „מה הפעיל, מה ההשפעה, מה השורש”; סיכום של גרסה צריך „מה
השתנה, מה נשבר, מה לעשות לפני השדרוג”. הנחיה אחת לשניהם הייתה בינונית לשניהם.

**מקבול.** עשר כתבות, קריאה אחת כל אחת; במקום לחכות לכל אחת בתורה, רצות שלוש בו־זמנית. הקוד
ב־`asyncio` עם **סמפור** (semaphore) שמגביל את מספר הקריאות הפתוחות; הלקוח הסינכרוני שלנו רץ
ב־`asyncio.to_thread`. למה שלוש ולא עשר? מגבלות הקצב (פרק 11): עשר בקשות באותה שנייה הן 429.
הניסוי מודד: סדרתי מול מקבילי, אותן עשר כתבות, אותן תשובות, זמן שונה פי שניים עד שלושה.

## 19.3 מתי אוטונומיה מוצדקת

ארבעה קריטריונים, וכולם צריכים להתקיים:

| קריטריון | השאלה | שלב המחקר בפרויקט |
| --- | --- | --- |
| מורכבות | האם הצעד הבא תלוי במה שהתגלה בצעד הקודם? | כן: איזה פריט לקרוא תלוי במה החיפוש החזיר |
| ערך | האם התוצאה שווה כמה קריאות ולא אחת? | כן, לשלושת הסיפורים הראשיים בלבד |
| היתכנות | האם הכלים מספיקים, והמודל מצליח ברוב המקרים? | כן: חיפוש וקריאה, ומדדנו |
| מחיר הטעות | אם הסוכן טועה, מה קורה? | סיפור עם הקשר חסר. לא שליחה שגויה; השליחה אינה בידי הסוכן |

כשאחד מהם לא מתקיים, תהליך עבודה. בפרויקט, כל שלב מלבד המחקר נכשל בקריטריון המורכבות: הקוד
יודע מה הבא.

## 19.4 הלולאה

הלולאה היא פרק 10 עם ארבעה דברים נוספים: מצב, תקציבים, סיבות עצירה ומעקב.

<div dir="ltr" align="left">

```python
@dataclass
class AgentState:
    question: str
    run_id: str
    history: list[dict]      # explicit Interactions steps: user_input, function_call, function_result, model_output
    sources: list[str]       # what was actually read
    steps: int               # model calls so far
    tokens: int
    seconds: float
    status: Literal["running", "done"]
    stop_reason: StopReason | None   # answered | max_steps | timeout | token_budget | loop_detected | error
    answer: str
    trace: list[TraceRecord]
```

</div>

| רכיב | למה הוא במצב |
| --- | --- |
| היסטוריה מפורשת | כדי שהריצה תהיה ניתנת לשמירה ולהמשכה בלי להסתמך על זיכרון בצד השרת (פרק 20) |
| מקורות | מה שנקרא בפועל, מהכלים, לא מה שהמודל טוען שקרא |
| צעדים, טוקנים, שניות | שלושת התקציבים. צעדים לבד לא מספיקים: קריאה אחת יכולה לקחת דקה או עשרת אלפים טוקנים |
| סיבת עצירה | כל ריצה מסתיימת בסיבה מפורשת. „נגמר התקציב” היא תוצאה תקינה, לא חריגה |
| מעקב | רשומה לכל קריאת מודל ולכל קריאת כלי: מה, כמה, כמה זמן |

הלולאה עצמה:

<div dir="ltr" align="left">

```python
while True:
    if a budget is spent: return finish(state, reason)
    interaction = backend.create(history=state.history, tools=declarations(tools), system=system)
    count steps, tokens, seconds; record a trace line
    calls = function_call steps in the interaction
    if not calls: state.answer = output_text; return finish(state, "answered")
    if guard vetoes this round: return finish(state, guard's reason)        # chapter 20
    for each call: append function_call; dispatch safely; append function_result; record trace
    on_step(state)                                                           # chapter 20 saves here
```

</div>

שלוש החלטות שראוי לשים לב אליהן:

- **הסדר של הבדיקות.** התקציב נבדק *לפני* כל קריאה, לא אחרי. קריאה שחורגת מהתקציב לא מתבצעת.
- **כישלון של הקריאה למודל** הופך לסיבת עצירה `error` עם הרשומה במעקב; הריצה מסתיימת מסודר,
  והקוד שקרא לה יודע מה קרה.
- **`on_step` אחרי סבב שלם.** המצב נשמר רק כשההיסטוריה עקבית: כל קריאה עם התוצאה שלה. זה מה
  שיאפשר המשכה בפרק 20.

והמשפט שחשוב לזכור על כל הלולאה: **המודל בוחר איזה כלי ומתי; הקוד קובע אם מותר, כמה זמן, וכמה.**

## 19.5 תכנון כטיוטה

מודלים שמתבקשים „לתכנן קודם” מייצרים רשימת צעדים ואז מבצעים אותה גם כשהצעד הראשון כבר
הראה שהתוכנית שגויה. בלולאה שלנו התכנון קיים בהוראות המערכת כהנחיה רכה („חפש קודם, קרא עד
שלושה פריטים, עצור כשאפשר לענות”), והמצב האמיתי של המשימה הוא ההיסטוריה, לא תוכנית. אם צריך
תוכנית מפורשת, היא טיוטה שנבדקת מחדש בכל צעד, ובמקרה הזה דפוס המתזמר (19.2) מתאים יותר
מסוכן יחיד.

## 19.6 עיצוב כלים לסוכנים

הכלים של סוכן המחקר מלמדים ארבעה כללים:

- **קטנים ומורכבים.** `search_feeds` מחזיר מזהים וסיכומים; `read_item` מחזיר טקסט מלא לפי מזהה.
  המודל בוחר מה לקרוא במקום לקבל הכול. כלי אחד „חפש וקרא הכול” היה מציף את ההקשר בכל סבב.
- **התיאור אומר מתי.** „Call this first” ו־„Use it for the items you intend to cite” מכוונים את
  הסדר בלי לכפות אותו.
- **לקריאה בלבד כברירת מחדל.** הסוכן לא שולח, לא מוחק, לא כותב. מה שלא קיים כלי לא יקרה (פרק
  10). כלי עם תופעות לוואי מקבלים טיפול בפרק 20.
- **רשת רק כשמבקשים.** `fetch_url` נכנס לרשימה רק עם `allow_network=True`, ורק לכתובות שהופיעו
  בפריט שנקרא.

הכלים הם מקומיים בכוונה: קובץ של 20 פריטי חדשות מומצאים. זה הופך את הדמו לחוזר ואת הבדיקות
לאפשריות; בפרויקט, אותם כלים יקראו מהמסד שמילא שלב האיסוף.

## 19.7 בדיקת סוכן

הלולאה נבדקת בלי מודל: `FakeBackend` מחזיר רצף של תשובות מתוסרטות (סבב עם קריאת חיפוש, סבב עם
שתי קריאות קריאה, תשובה סופית), והבדיקה מאשרת את סיבת העצירה, את המקורות, את מספר הצעדים
והטוקנים, את צורת ההיסטוריה ואת רצף המעקב. התקציבים נבדקים עם תסריט שלא נגמר אף פעם: שניים
ועוצר ב־`max_steps`; שעון מוזרק שקופץ ועוצר ב־`timeout`; טוקנים ועוצר ב־`token_budget`. ובדיקה
שה־`guard` יכול להטיל וטו, ושחריגה מהמודל הופכת ל־`error`. זה מה שאומר „סוכן שאפשר לבדוק”: כל
סיבת עצירה נבדקת פעם אחת, בלי רשת.

## 19.8 בפרויקט

- **הצינור הוא תהליך עבודה:** איסוף, חילוץ, סיכום (מקבול עם סמפור), דירוג, איחוד כפילויות, הרכבה,
  שליחה. הקוד מחליט על כל צעד. ניתוב קובע את הנחיית הסיכום לפי סוג הכתבה.
- **שלב אחד הוא סוכן:** המחקר לשלושת הסיפורים הראשיים, עם `search_feeds` ו־`read_item` על המסד
  של היום, `fetch_url` לקישורים מתוך הכתבה, שישה צעדים, תשעים שניות, ותקציב טוקנים. סיבת העצירה
  נרשמת בדוח הריצה.
- **אבן דרך 4** בונה בדיוק את זה, והמעקב של הלולאה הופך למעקב של הצינור בחלק ז.

## סיכום

- סוכן: המודל מחליט על הזרימה. תהליך עבודה: הקוד מחליט. הכי פחות אוטונומיה שעובדת.
- חמישה דפוסים: שרשור, ניתוב, מקבול, מתזמר ועובדים, מעריך ומשפר. ניתוב ומקבול בקוד השבוע.
- אוטונומיה דורשת מורכבות, ערך, היתכנות, ומחיר טעות נמוך. בפרויקט: רק המחקר.
- הלולאה: מצב מפורש, תקציבים נבדקים לפני כל קריאה, סיבת עצירה תמיד, מעקב לכל קריאה, שמירה אחרי
  סבב שלם.
- תכנון הוא טיוטה; כלים קטנים, מתוארים, לקריאה בלבד; הכול נבדק עם backend מתוסרט.

## מונחים לזכור

| מונח בעברית | באנגלית | במשפט אחד |
| --- | --- | --- |
| סוכן | agent | המודל מחליט על זרימת הבקרה: כלים, המשך, עצירה |
| תהליך עבודה | workflow | הקוד מחליט על הזרימה; המודל ממלא צעדים |
| ניתוב | routing | סיווג קודם, הנחיה לפי סוג |
| מקבול | parallelization | כמה קריאות בו־זמנית, עם גבול |
| סמפור | semaphore | מונה שמגביל כמה פעולות פתוחות |
| מתזמר ועובדים | orchestrator–workers | מודל מפרק, עובדים מבצעים, מאחדים |
| מעריך ומשפר | evaluator–optimizer | יצירה, ביקורת לפי קריטריון, חזרה |
| מצב הסוכן | agent state | היסטוריה, מקורות, תקציבים, סיבת עצירה, מעקב |
| תקציב | budget | צעדים, שניות, טוקנים; נבדק לפני כל קריאה |
| סיבת עצירה | stop reason | למה הריצה נגמרה; תמיד מפורשת |

## טעויות נפוצות

- **לקרוא לכל דבר סוכן** ולבנות לולאה למשימה שהקוד יודע לפרק. יקר, לא צפוי, קשה לבדוק.
- **תקציב צעדים בלבד.** קריאה אחת יכולה לקחת דקה. שלושה תקציבים.
- **לבדוק תקציב אחרי הקריאה.** הקריאה שחרגה כבר שולמה.
- **לסמוך על „המקורות” שהמודל מצטט.** המקורות הם מה שהכלים החזירו בפועל.
- **כלי ענק שמחזיר הכול.** ההקשר מתמלא בסבב אחד; כלים קטנים ובחירה.
- **לשמור מצב באמצע סבב.** היסטוריה עם קריאה בלי תוצאה לא ניתנת להמשכה.

## שאלות ראיון

1. **מה ההבדל בין סוכן לתהליך עבודה, ומתי תבני כל אחד?** בתהליך עבודה הקוד מחליט על הצעד הבא
   ובסוכן המודל מחליט. בונים סוכן רק כשהצעד הבא תלוי במה שהתגלה, כשהערך מצדיק כמה קריאות,
   כשהכלים מספיקים, וכשמחיר הטעות נמוך. אחרת תהליך עבודה: צפוי, זול, נבדק צעד־צעד.
2. **מה נמצא במצב של סוכן, ולמה?** היסטוריה מפורשת (להמשכה), מקורות שנקראו בפועל, צעדים וטוקנים
   ושניות (שלושה תקציבים), סיבת עצירה מפורשת, ומעקב לכל קריאה. בלי זה אי אפשר לעצור, להמשיך, או
   להסביר מה קרה.
3. **למה גבול צעדים לא מחליף זמן קצוב?** כי צעד אחד יכול להימשך דקה, ושישה צעדים יכולים לעלות
   עשרות אלפי טוקנים. שלושה תקציבים נבדקים לפני כל קריאה, וכל אחד הוא סיבת עצירה משלו.
4. **איך בודקים סוכן?** backend מתוסרט שמחזיר קריאות כלים ותשובה; בדיקה של סיבת העצירה,
   המקורות, צורת ההיסטוריה והמעקב; ותסריט אינסופי לכל תקציב, עם שעון מוזרק לזמן. בלי רשת.
